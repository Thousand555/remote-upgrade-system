4. 链接脚本深入：链接脚本语法解析、ROM与RAM布局设计、Section的分配与对齐

好，咱们今天来啃一块硬骨头——链接脚本。说实话，我刚入行那会儿，看到链接脚本就头疼。一堆花括号、星号、点号，感觉像天书。但后来我发现，这东西其实就是一张「地图」，告诉编译器你的代码和数据该往哪儿放。

你想想看，嵌入式系统里，ROM（Flash）和RAM是两码事。代码通常放在ROM里，上电就能跑。变量呢？得放在RAM里，因为要读写。链接脚本就是干这个的——把不同的段（Section）分配到正确的地方。

4.1 链接脚本语法解析

先看一个最简的链接脚本长什么样。我习惯从实际例子入手，这样好理解。

ENTRY(Reset_Handler)

MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 512K
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 128K
}

SECTIONS
{
    .text :
    {
        *(.isr_vector)
        *(.text)
        *(.text.*)
        *(.rodata)
        . = ALIGN(4);
        _etext = .;
    } > FLASH

    .data :
    {
        _sdata = .;
        *(.data)
        *(.data.*)
        . = ALIGN(4);
        _edata = .;
    } > RAM AT> FLASH

    .bss :
    {
        _sbss = .;
        *(.bss)
        *(.bss.*)
        *(COMMON)
        . = ALIGN(4);
        _ebss = .;
    } > RAM
}

嗯，看着是不是有点眼熟了？咱们一行行拆开讲。

ENTRY() 定义了程序入口点。说白了就是告诉CPU：上电后第一条指令在哪儿。我见过有人忘了写这个，结果程序跑飞了，查了半天才发现是入口没指定。

MEMORY 块定义了两块物理存储区域。FLASH从0x08000000开始，大小512KB，属性是rx（可读可执行）。RAM从0x20000000开始，大小128KB，属性是rwx（可读可写可执行）。

这里有个细节：属性里的x表示能否执行代码。有些MCU的RAM也能执行代码，但大部分情况下，我们只在RAM里放数据，所以写成rw就够了。

SECTIONS 块是核心。它描述了每个段怎么分配。

关键点：链接脚本里的「点号（.）」代表当前地址计数器。你可以把它理解成一个指针，指向当前正在分配的位置。

4.2 ROM与RAM布局设计

ROM和RAM的布局，说白了就是回答两个问题：

  • 代码放哪儿？—— 通常放ROM
  • 变量放哪儿？—— 通常放RAM

但事情没那么简单。你想想看，全局变量初始值怎么办？它们在ROM里有个「镜像」，上电后要拷贝到RAM里。这就是.data段的处理逻辑。

我在项目中遇到过一个问题：有个同事把一个大数组定义成全局变量，没初始化。结果程序跑起来后，数组里的值全是乱的。为什么？因为.bss段在启动代码里被清零了，但.data段需要从ROM拷贝初始值。他那个数组没初始化，属于.bss段，但启动代码没处理好，导致数据混乱。

典型的ROM/RAM布局如下：

段名 存储位置 运行位置 说明
.isr_vector ROM起始 ROM 中断向量表，必须从0地址开始
.text ROM ROM 代码和只读数据
.rodata ROM ROM 常量字符串、const变量
.data ROM（镜像） RAM 已初始化全局变量
.bss 无 RAM 未初始化全局变量
堆/栈 无 RAM末尾 动态分配和函数调用

注意看.data段那一行：它在ROM里有个「镜像」，但运行时在RAM里。这就是为什么链接脚本里写的是 > RAM AT> FLASH。意思是：运行时在RAM，但加载地址在FLASH。

小技巧：启动代码里一定要有从ROM拷贝.data到RAM的循环，以及清零.bss段的循环。我见过有人忘了写这个，结果全局变量初始值全丢了。

4.3 Section的分配与对齐

Section分配，说白了就是把不同的代码和数据归类，放到不同的段里。对齐呢？就是让数据在内存里按2的幂次方地址存放。

为什么要对齐？因为CPU访问对齐的数据更快。有些ARM内核甚至不支持非对齐访问，一访问就触发异常。嗯，这里要注意：

  • 4字节对齐：地址末尾两位是00
  • 8字节对齐：地址末尾三位是000
  • 16字节对齐：地址末尾四位是0000

链接脚本里用 . = ALIGN(4) 来强制对齐。这行代码的意思是：把当前地址向上取整到4的倍数。

举个例子：假设当前地址是0x20000003，执行 . = ALIGN(4) 后，地址变成0x20000004。跳过了3个字节。

我曾经踩过一个坑：有个结构体里定义了uint8_t和uint32_t混排的成员，没加__packed属性。结果结构体大小比预期多了3个字节，因为编译器自动填充了对齐空隙。后来我在链接脚本里加了对齐检查，才发现了问题。

再看一个更复杂的例子——自定义段：

.my_custom_section :
{
    . = ALIGN(4);
    _smy_custom = .;
    *(.my_custom_section)
    *(.my_custom_section.*)
    . = ALIGN(4);
    _emy_custom = .;
} > RAM

这个段有什么用？比如你想把一些关键数据放在RAM的特定区域，方便调试或者DMA访问。在C代码里这样声明：

__attribute__((section(".my_custom_section"))) 
uint32_t critical_buffer[1024];

这样，critical_buffer就被放到了你指定的位置。我经常用这个技巧来管理DMA缓冲区，确保它们不会和其他变量混在一起。

警告：自定义段的名字不要和系统保留段（如.text、.data、.bss）重名。否则链接器会报错，或者更糟——静默覆盖。

4.4 链接脚本中的符号导出

链接脚本里定义的符号，比如 _sdata、_edata，可以在C代码里直接引用。怎么用？用extern声明：

extern uint32_t _sdata;
extern uint32_t _edata;
extern uint32_t _sbss;
extern uint32_t _ebss;

void startup_copy_data(void)
{
    uint32_t *src = &_sdata;  // 注意：这里取的是地址
    uint32_t *dst = ...;      // RAM目标地址
    uint32_t len = &_edata - &_sdata;
    // 执行拷贝...
}

这里有个容易搞混的地方：链接脚本里定义的符号，在C代码里取地址时，得到的是链接脚本里那个位置的值。说白了，&_sdata 就是.data段在ROM里的起始地址。

我刚开始学的时候，总搞不清这个。后来想通了：链接脚本里的符号，本质上就是一个地址常量。你在C代码里用extern声明它，然后取它的地址，就得到了那个地址值。

4.5 实际项目中的布局策略

在实际项目中，ROM和RAM的布局要考虑很多因素。我总结了几条经验：

  1. 中断向量表必须放在ROM起始地址。这是硬件规定的，没得商量。
  2. 代码段尽量紧凑。ROM空间有限，别浪费。可以用 -Os 优化选项。
  3. RAM分区管理。把.data、.bss、堆、栈分开，避免互相覆盖。
  4. 栈大小要留余量。我一般给栈分配RAM的1/4，再根据实际调试调整。
  5. 考虑OTA升级。如果要做远程升级，ROM里要预留两个Bank，一个跑当前程序，一个存升级包。

举个例子，一个支持OTA的布局可能是这样的：

MEMORY
{
    FLASH_BANK1 (rx)  : ORIGIN = 0x08000000, LENGTH = 256K
    FLASH_BANK2 (rx)  : ORIGIN = 0x08040000, LENGTH = 256K
    RAM         (rwx) : ORIGIN = 0x20000000, LENGTH = 128K
}

这样，Bank1跑程序，Bank2存升级包。切换时只需要修改中断向量表的偏移量就行。
