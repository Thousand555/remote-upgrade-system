第2章：嵌入式系统基础：ARM Cortex-M架构概述、存储器映射与启动流程、中断向量表详解

2.1 ARM Cortex-M 架构到底是个啥？

做 Bootloader 开发，绕不开 ARM Cortex-M 系列。我个人习惯把 Cortex-M 看作一个「极度精简、为嵌入式而生」的处理器家族。它不像 Cortex-A 那样跑 Linux，也不像 Cortex-R 那样搞实时控制，它就是为了单片机场景设计的——低功耗、低成本、中断响应快。

你想想看，我们平时用的 STM32、GD32、NXP LPC 系列，内核基本都是 Cortex-M0、M3、M4 或者 M7。它们有个共同特点：采用哈佛架构，指令总线和数据总线分开。这意味着取指令和读写数据可以同时进行，效率比冯·诺依曼架构高不少。

我记得刚入行那会儿，有个老工程师跟我说：「搞懂 Cortex-M 的寄存器模型，你就掌握了 Bootloader 的一半。」当时我不信，后来踩了坑才明白——确实如此。

Cortex-M 内核有几个关键寄存器，你必须要记住：

  • R0-R12：通用寄存器，随便用
  • R13 (SP)：堆栈指针，分 MSP 和 PSP
  • R14 (LR)：链接寄存器，保存返回地址
  • R15 (PC)：程序计数器，指向当前指令
  • xPSR：程序状态寄存器，存标志位

嗯，这里要注意：Cortex-M 的堆栈是满递减的。什么意思？就是 SP 初始指向栈顶，压栈时 SP 先减，再存数据。这个细节在写 Bootloader 的汇编启动代码时特别重要，搞反了程序直接跑飞。

核心要点：Cortex-M 只支持 Thumb/Thumb-2 指令集，不支持 ARM 指令集。这意味着所有代码必须是 16 位或 32 位混合的 Thumb 指令。你在写 Bootloader 时，编译器选项一定要选对，否则链接出来的二进制文件根本跑不起来。

2.2 存储器映射——芯片的「地址地图」

每个 Cortex-M 芯片都有一个固定的存储器映射。说白了，就是芯片厂商把 4GB 的地址空间划分成几个区域，每个区域干不同的事。ARM 公司规定了一个标准布局，但具体怎么分配，还得看芯片厂商。

标准映射是这样的：

地址范围 区域名称 用途
0x00000000 - 0x1FFFFFFF Code 区 存放程序代码，通常映射到 Flash
0x20000000 - 0x3FFFFFFF SRAM 区 存放运行时数据、堆栈
0x40000000 - 0x5FFFFFFF 外设区 映射 GPIO、UART、TIM 等外设寄存器
0x60000000 - 0x9FFFFFFF 外部 RAM 区 扩展内存，比如 SDRAM
0xE0000000 - 0xE00FFFFF 系统控制区 NVIC、MPU、SysTick 等内核外设

我在项目中遇到过一个问题：某款国产芯片的 Flash 起始地址不是 0x08000000，而是 0x00000000。结果我按照 STM32 的习惯写了链接脚本，Bootloader 死活跳不到应用程序。查了两天才发现——不同芯片的 Flash 基地址可能不一样。所以，拿到一个新芯片，第一件事就是看数据手册的存储器映射章节。

我的建议：写 Bootloader 时，把 Flash 和 RAM 的起始地址、大小定义成宏。这样换芯片时只需要改几个宏定义，不用动核心逻辑。比如：

#define FLASH_BASE     0x08000000
#define FLASH_SIZE     0x00100000  // 1MB
#define RAM_BASE       0x20000000
#define RAM_SIZE       0x00020000  // 128KB

2.3 启动流程——芯片上电后发生了什么？

Cortex-M 的启动流程，说白了就三步：

  1. 从地址 0x00000000 读取 SP 初始值
  2. 从地址 0x00000004 读取 PC 初始值（即 Reset_Handler 地址）
  3. 跳转到 Reset_Handler 执行

为什么会这样设计？因为 Cortex-M 硬件自动完成了这两次读取，不需要像传统 ARM 那样先执行一段汇编代码来初始化堆栈。这大大简化了启动流程。

但这里有个坑：地址 0x00000000 和 0x00000004 存放的到底是什么？它们不是代码，而是中断向量表的前两个条目。第一个条目是栈顶指针，第二个条目是复位向量。

我刚开始做 Bootloader 时，以为只要把应用程序烧到 Flash 里，复位后就能自动运行。结果发现——芯片复位后永远从 0x00000000 开始执行。如果你的 Bootloader 在 0x08000000，应用程序在 0x08010000，那复位后芯片根本不知道应用程序的存在。

所以，Bootloader 的核心任务之一就是：在适当的时候，把控制权交给应用程序。怎么交？通过修改 PC 指针，跳转到应用程序的 Reset_Handler。

注意：跳转前必须做三件事：

  • 关闭所有外设中断（防止跳转后产生意外中断）
  • 禁用系统滴答定时器 SysTick
  • 将主堆栈指针 MSP 设置为应用程序的栈顶地址

我曾经因为没关 SysTick，跳转到应用程序后，SysTick 中断还在用 Bootloader 的中断向量表，结果一进中断就跑飞。排查了整整一个下午。

2.4 中断向量表详解——芯片的「紧急联络簿」

中断向量表，说白了就是一张表。表里按顺序记录了每个中断对应的处理函数地址。当某个中断发生时，硬件自动从表中找到对应的地址，跳过去执行。

Cortex-M 的中断向量表长这样：

偏移地址 异常号 名称 描述
0x00 - SP_initial 栈顶指针初始值
0x04 1 Reset_Handler 复位中断
0x08 2 NMI_Handler 不可屏蔽中断
0x0C 3 HardFault_Handler 硬错误
0x10 4 MemManage_Handler 内存管理错误（M3/M4/M7）
0x14 5 BusFault_Handler 总线错误（M3/M4/M7）
0x18 6 UsageFault_Handler 用法错误（M3/M4/M7）
... ... ... ...
0x40 16 IRQ0 第一个外设中断

注意看，前 16 个是系统异常（包括复位、NMI、各种 Fault），从第 16 个开始才是外设中断。每个条目占 4 字节，所以第 n 个中断的地址偏移就是 0x40 + n * 4。

在 Bootloader 开发中，中断向量表有个极其重要的概念——向量表重定位。什么意思？就是告诉硬件：「别去 0x00000000 找向量表了，去 0x08010000 找。」

Cortex-M 提供了一个寄存器叫 VTOR（Vector Table Offset Register），专门干这个事。你只需要把应用程序的向量表基地址写进去，硬件就会自动从新地址读取中断处理函数。

代码实现很简单：

/* 设置向量表偏移 */
#define APP_VECTOR_TABLE  0x08010000

void jump_to_app(void)
{
    uint32_t app_sp;
    uint32_t app_pc;
    void (*app_entry)(void);
    
    /* 1. 从应用程序向量表读取栈顶指针 */
    app_sp = *(volatile uint32_t *)APP_VECTOR_TABLE;
    
    /* 2. 从应用程序向量表读取复位向量 */
    app_pc = *(volatile uint32_t *)(APP_VECTOR_TABLE + 4);
    
    /* 3. 设置主堆栈指针 */
    __set_MSP(app_sp);
    
    /* 4. 设置向量表偏移 */
    SCB->VTOR = APP_VECTOR_TABLE;
    
    /* 5. 跳转到应用程序 */
    app_entry = (void (*)(void))app_pc;
    app_entry();
}

关键点：设置 VTOR 必须在跳转之前完成。否则，应用程序里一旦发生中断，硬件还是去原来的向量表找处理函数，结果找到的是 Bootloader 的，程序就乱套了。

另外，有个细节容易被忽略：Cortex-M0/M0+ 没有 VTOR 寄存器。这意味着它们不支持向量表重定位。那怎么办？只能用「复制向量表到 SRAM」的方式，或者用「重映射」功能把 Flash 的某段地址映射到 0x00000000。具体怎么做，后面章节会详细讲。

2.5 小结

这一章的内容，说白了就是 Bootloader 的「地基」。搞懂了 Cortex-M 的架构、存储器映射、启动流程和中断向量表，你才能理解 Bootloader 为什么要那样写、那样跳转。

我个人觉得，学 Bootloader 最忌讳的就是「知其然而不知其所以然」。很多人照着网上的代码抄一遍，能跑就完事了。但一旦遇到芯片换型号、Flash 地址变化、中断异常等问题，就完全抓瞎。

所以，我建议你把这一章的内容吃透。尤其是中断向量表那部分，多画几张图，把地址、偏移、内容对应关系搞清楚。后面讲「Bootloader 跳转应用程序」时，你会回来感谢我的。
