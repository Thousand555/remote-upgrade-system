第16章 OTA升级原理：从架构到实战

各位同学，今天我们来聊聊OTA升级。说实话，这个主题我特别有感触。早些年做嵌入式开发，升级固件还得拿着烧录器跑到现场，那叫一个折腾。后来OTA技术普及了，远程就能搞定，但坑也多了不少。今天我就把这些年踩过的坑、总结的经验，一次性讲清楚。

16.1 OTA系统架构设计

先说说整体架构。一个完整的OTA系统，说白了就三块：云端、设备端、还有连接它们的那条路。

云端部分，我习惯把它拆成三个服务：

  • 固件管理服务：负责存固件、版本管理、差分包生成。我在项目中见过有人把固件直接扔在对象存储里，版本号用文件名管理...嗯，后来出过问题，版本号搞混了，设备刷了旧固件。
  • 设备管理服务：记录每台设备的当前版本、升级状态、设备信息。这个很重要，没有它你都不知道哪些设备该升级。
  • 升级调度服务：决定什么时候推升级、推给谁、怎么推。我建议做灰度升级，先推1%的设备看看效果。

设备端，我一般分三层：

  • 通信层：负责和云端握手、下载数据。协议我推荐用MQTT或者CoAP，轻量级，适合嵌入式。
  • 升级管理层：核心逻辑在这。校验固件、备份当前系统、写入新固件、回滚处理。
  • 应用层：你的业务代码。升级过程中应用层要配合，比如暂停业务、保存现场数据。

架构设计要点：

  • 云端和设备端之间要有心跳机制，我习惯30秒一次
  • 设备端必须保留两个固件分区：当前运行区和备份区
  • 升级失败要有自动回滚能力，这个我吃过亏

16.2 云端与设备端交互流程

交互流程，我画过无数遍流程图。这里我直接说关键步骤：

  1. 设备上报状态：设备上线后，主动上报当前固件版本、硬件型号、剩余存储空间。我见过有人不上报硬件型号，结果推送了不兼容的固件，设备直接变砖。
  2. 云端检查更新：云端收到上报后，查一下有没有新版本。如果有，返回升级包信息：版本号、包大小、校验值、下载地址。
  3. 设备下载固件：设备拿到下载地址后，开始下载。我建议分片下载，每片1KB-4KB，边下载边校验。为什么？网络不稳定，整包下载容易失败。
  4. 固件校验：下载完成后，做完整性校验。我一般用MD5或者SHA256，别偷懒只用CRC，安全性不够。
  5. 备份当前固件：把当前运行固件备份到备份分区。这一步很多人忽略，但关键时刻能救命。
  6. 写入新固件：把新固件写入运行分区。写入过程中不要断电，我建议加个电容做掉电保护。
  7. 重启验证：重启后，设备用新固件启动。启动成功后上报新版本号，云端标记升级完成。

我的经验：交互流程中，我最看重的是「断点续传」。设备下载到一半断网了，下次能接着下载，而不是从头再来。这个功能在弱网环境下特别重要。

16.3 差分升级技术简介

差分升级，说白了就是只传输变化的部分。你想想看，固件可能10MB，但每次只改了几KB的代码，全量下载太浪费流量了。

差分算法原理：

  • 对比新旧两个固件，找出差异部分
  • 生成一个差分包，里面只包含变化的数据和位置信息
  • 设备端用旧固件+差分包，还原出新固件

常用的差分算法有几种：

算法 特点 适用场景
bsdiff 压缩率高，但内存占用大 资源丰富的设备
hdiffpatch 速度较快，内存适中 大多数嵌入式设备
xdelta 实现简单，但压缩率一般 资源受限的设备

我在项目中用过hdiffpatch，效果不错。差分包大小通常只有全量包的5%-20%，省流量效果很明显。

注意：差分升级有个前提——设备上必须有旧固件的完整副本。如果旧固件被损坏了，差分升级就玩不转了。所以我建议：差分升级失败时，自动回退到全量升级模式。

16.4 避坑指南

最后，我分享几个实战中遇到的坑：

  • 版本号管理：我曾经见过版本号用字符串比较的，结果"1.9.0"比"1.10.0"大...后来我统一用整数版本号，比如1009001这种格式。
  • 升级超时处理：设备下载固件时，如果长时间没收到数据，要主动超时重试。我一般设30秒超时，重试3次。
  • 存储空间预留：升级过程中需要额外空间存放下载的固件。我建议预留至少两倍固件大小的空间。
  • 测试覆盖：OTA升级一定要做异常测试：断网、断电、存储满、版本不匹配...这些场景都要覆盖到。
