5. 启动代码分析：汇编启动代码详解、堆栈初始化、BSS段清零与数据段拷贝

好，咱们今天来聊聊启动代码里最核心的几个动作。说实话，很多做嵌入式开发的朋友，写了几年C语言，却从来没仔细看过启动文件。我刚开始带团队的时候，有个同事遇到一个诡异的问题——程序跑飞，查了三天，最后发现是BSS段没清零。嗯，从那以后，我要求每个新人都必须手写一遍启动代码。

5.1 汇编启动代码的结构

启动代码，说白了就是芯片上电后执行的第一段程序。它通常放在复位向量指向的位置。我个人习惯把启动代码分成三个阶段：

  1. 第一阶段：异常向量表设置——告诉CPU，发生中断该去哪
  2. 第二阶段：系统初始化——堆栈、时钟、内存控制器
  3. 第三阶段：C环境准备——BSS清零、数据段拷贝、跳转main

你想想看，如果没有这些准备工作，C语言里的全局变量初始值从哪来？局部变量又该存在哪？

5.2 堆栈初始化——给C语言搭个台子

堆栈初始化是启动代码里最容易被忽视的一步。我记得有一次调试一个STM32的项目，程序一调用函数就死机。查了半天，发现是堆栈指针SP没有正确设置。

堆栈初始化的核心就一句话：把SP指向一块可读写的RAM区域。但这里有几个坑：

避坑指南：

  • 堆栈地址必须4字节对齐（ARM Cortex-M系列要求8字节对齐）
  • 堆栈大小要预留足够——我曾经遇到过递归调用把堆栈撑爆的情况
  • 多模式处理器（如ARM7）需要为每种模式单独设置堆栈

来看一个典型的堆栈初始化代码：

; 设置堆栈指针
; 假设堆栈从RAM末尾开始向下生长
LDR   R0, =_stack_end    ; 加载堆栈结束地址
MSR   MSP, R0            ; 设置主堆栈指针

; 对于ARM7等支持多种模式的处理器
; 还需要设置IRQ、FIQ、SVC等模式的堆栈
CPS   #0x12              ; 切换到IRQ模式
LDR   SP, =_irq_stack_top
CPS   #0x11              ; 切换到FIQ模式
LDR   SP, =_fiq_stack_top
CPS   #0x13              ; 切换回SVC模式
LDR   SP, =_svc_stack_top

这里有个小技巧：我习惯在堆栈区域的两端填充0xDEADBEEF这样的魔数，运行时定期检查这些值有没有被覆盖。这样能及时发现堆栈溢出。

5.3 BSS段清零——别让野值害了你

BSS段存放的是未初始化的全局变量和静态变量。C语言标准规定，这些变量在程序启动时必须为0。但硬件可不会帮你做这件事——RAM上电后的值是随机的。

为什么会这样？因为RAM本身没有"初始值"这个概念。你想想看，SRAM的每个存储单元上电后可能是0也可能是1，完全取决于物理状态。

核心要点：

BSS段清零必须在调用任何C函数之前完成。否则，你声明的 int flag; 可能一开始就是0x5A5A5A5A，程序逻辑直接崩掉。

清零的代码其实很简单：

; BSS段清零
; _bss_start 和 _bss_end 由链接脚本定义
LDR   R0, =_bss_start
LDR   R1, =_bss_end
MOV   R2, #0

bss_loop:
  CMP   R0, R1
  BHS   bss_done        ; 如果R0 >= R1，跳转结束
  STR   R2, [R0], #4    ; 写入0，地址加4
  B     bss_loop
bss_done:

我在项目中遇到过一个问题：BSS段很大（比如几百KB），用这种逐字清零的方式太慢了。后来我改用DMA来加速，或者用更宽的寄存器（比如NEON指令一次清零16字节）。

5.4 数据段拷贝——把初始值搬进RAM

数据段存放的是已初始化的全局变量和静态变量。比如 int count = 100;，这个100的初始值存在Flash里，但运行时需要搬到RAM中才能读写。

数据段拷贝的本质就是：从Flash（加载域）复制到RAM（运行域）。链接脚本里通常用 LOADADDR 和 ADDR 来区分这两个地址。

符号 含义 示例
_data_load 数据在Flash中的起始地址 0x08001000
_data_start 数据在RAM中的起始地址 0x20000000
_data_end 数据在RAM中的结束地址 0x20000100

拷贝代码：

; 数据段拷贝
LDR   R0, =_data_load    ; 源地址（Flash）
LDR   R1, =_data_start   ; 目标地址（RAM）
LDR   R2, =_data_end

copy_loop:
  CMP   R1, R2
  BHS   copy_done
  LDR   R3, [R0], #4     ; 从Flash读4字节
  STR   R3, [R1], #4     ; 写入RAM
  B     copy_loop
copy_done:

个人经验：

如果数据段很大（比如几百KB），逐字拷贝确实慢。我建议用以下优化：

  • 使用LDM/STM指令一次拷贝多个寄存器
  • 开启指令缓存（I-Cache）加速Flash读取
  • 如果芯片支持，用DMA做后台拷贝

5.5 完整的启动流程

把这些步骤串起来，一个典型的启动流程就是：

  1. 设置异常向量表（通常放在0地址）
  2. 初始化堆栈指针（SP）
  3. 清零BSS段
  4. 拷贝数据段
  5. 初始化系统时钟和外设（可选，有时放在main里做）
  6. 跳转到C语言的main函数

最后跳转的代码通常是这样：

; 跳转到main函数
; 注意：有些编译器要求先调用__libc_init_array
BL    main
; 如果main返回，进入死循环
B     .

嗯，这里要注意：有些RTOS或复杂系统会在跳转main之前先初始化堆管理器（malloc的底层支持），或者初始化C++的全局对象构造函数。这些细节取决于你的工具链。

5.6 常见问题与调试技巧

我总结几个实际项目中踩过的坑：

  • 堆栈设置太小——程序跑着跑着就进HardFault。解决办法：在链接脚本里加大堆栈，或者用静态分析工具检查最大堆栈使用量。
  • BSS段和data段地址重叠——链接脚本写错了，导致两个段指向同一块RAM。我曾经因为这个查了一整天，最后用map文件对比才发现。
  • 拷贝方向搞反——把RAM往Flash拷，结果Flash被写坏了（有些Flash支持自写，但速度极慢）。

调试建议：

启动代码出问题很难调试，因为此时调试器可能还没初始化好。我的做法是：

  • 在关键步骤后点亮一个LED，用肉眼观察执行到哪一步
  • 用逻辑分析仪抓GPIO电平变化
  • 在汇编代码里插入死循环，用调试器查看寄存器状态
