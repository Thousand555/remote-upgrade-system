第十三章：双备份启动策略

各位同学，今天我们来聊聊嵌入式系统里一个非常关键的话题——双备份启动。说白了，就是给系统准备两套“救生衣”。

我在做工业控制器项目时，遇到过设备OTA升级到一半断电的情况。结果呢？设备变砖了。客户差点把我们的售后电话打爆。从那以后，我深刻理解了双备份的重要性。

13.1 为什么需要双备份？

你想想看，现在的设备动不动就要远程升级。升级过程中要是断电、断网、或者固件本身有问题，系统就挂了。传统的单分区方案，就像走钢丝——只有一次机会。

双备份策略，说白了就是准备两个完全独立的系统分区。一个叫A分区，一个叫B分区。平时从A分区启动，升级时更新B分区。下次启动就切到B分区。万一B分区启动失败，还能回滚到A分区。

核心思想：永远保证至少有一个可用的系统副本。

13.2 A/B分区设计

分区布局其实很简单。我习惯把Flash分成这样：

| Bootloader | A分区 (系统) | B分区 (系统) | 数据分区 |

每个系统分区里，通常包含：

  • 分区头信息：版本号、校验值、启动计数
  • 内核镜像：操作系统内核
  • 文件系统：应用程序和配置

这里有个细节要注意——分区大小必须完全一致。为什么？因为升级时Bootloader要能无缝切换。我在一个项目里就吃过亏，A分区比B分区大了4KB，结果升级时总是写越界。

我的习惯：分区大小按Flash擦除块对齐，通常是64KB或128KB的整数倍。

13.3 启动计数机制

启动计数，说白了就是记录系统启动了多少次。每次启动时，Bootloader会把这个计数器加1。如果系统正常运行，应用层会把这个计数器清零。

为什么要这么做？

假设你升级了新固件，结果新固件有bug，启动后5秒就死机。如果没有启动计数，Bootloader永远不知道这个分区有问题。有了计数机制，Bootloader就能判断：

  1. 启动计数超过阈值（比如3次）
  2. 应用层没有清零
  3. 判定分区故障
  4. 自动切换到另一个分区
// 启动计数示例代码
#define BOOT_RETRY_LIMIT 3

typedef struct {
    uint32_t magic;        // 魔数，验证有效性
    uint32_t boot_count;   // 启动计数
    uint32_t version;      // 固件版本
    uint32_t crc32;        // 分区校验
} partition_header_t;

void bootloader_main() {
    partition_header_t *header = get_current_partition_header();
    
    if (header->magic != PARTITION_MAGIC) {
        // 分区损坏，切换到备份
        switch_to_backup_partition();
        return;
    }
    
    header->boot_count++;
    save_header(header);
    
    if (header->boot_count > BOOT_RETRY_LIMIT) {
        // 启动失败次数过多，回滚
        rollback_to_backup();
        return;
    }
    
    jump_to_partition();
}

注意：启动计数要保存在Flash里，而且要考虑磨损均衡。我曾经见过一个设备，因为频繁重启，Flash的同一个位置被写了几万次，直接报废了。

13.4 回滚机制

回滚，就是系统发现当前分区有问题，自动切回上一个正常的分区。这个机制说起来简单，实现起来有不少坑。

我总结了几种回滚触发条件：

  • 启动超时：系统启动超过30秒还没进入应用层
  • 看门狗复位：连续多次看门狗超时
  • 应用层主动请求：应用检测到严重错误，主动要求回滚
  • 校验失败：分区CRC校验不通过

回滚的流程大概是这样的：

1. Bootloader检测到当前分区异常
2. 标记当前分区为"失败"状态
3. 读取备份分区的状态
4. 如果备份分区有效，切换到备份分区
5. 如果备份分区也无效...嗯，那就只能进恢复模式了

关键点：回滚操作本身必须是原子性的。也就是说，要么成功切换，要么保持原样。不能出现切到一半断电，导致两个分区都不可用的情况。

13.5 故障检测与恢复

故障检测，说白了就是系统怎么知道自己出问题了。我常用的检测手段有：

检测项 检测方法 恢复策略
分区头校验 CRC32校验分区头 切换到备份分区
内核完整性 SHA256校验内核镜像 重新下载固件
启动超时 硬件看门狗监测 回滚到上一个版本
应用层心跳 应用定期刷新看门狗 系统复位
文件系统检查 fsck或类似工具 格式化并恢复默认配置

我曾经在一个物联网网关项目里，遇到过一种很隐蔽的故障——新固件能启动，但WiFi驱动有问题，导致设备连不上网。这种故障启动计数检测不出来，因为系统确实启动了。后来我加了一个“网络连通性检测”，应用层启动后如果30秒内连不上服务器，就主动触发回滚。

我的建议：故障检测要分层。Bootloader层做基础检测，应用层做功能检测。两层配合，才能覆盖大部分故障场景。

13.6 实战中的注意事项

最后，分享几个我在项目中踩过的坑：

  • 分区切换要加延迟：不要一检测到故障就立刻切换。有时候只是暂时的电压波动。我习惯等3次启动失败后再切换。
  • 保留恢复模式：两个分区都坏了怎么办？一定要留一个最小的恢复模式，能通过串口或USB刷固件。
  • 日志记录：每次切换分区都要记录原因。不然出了问题，你都不知道系统为什么来回切。
  • 测试要全面：模拟各种故障场景——升级中断电、写入坏块、分区损坏。我在实验室里专门搭了一套自动测试环境，跑了一周才放心。

嗯，双备份启动策略就讲到这里。说白了，就是给系统多留一条后路。做嵌入式开发，永远要假设最坏的情况会发生。准备好了，才能从容应对。
