第十五章：固件加密与安全启动

说到嵌入式安全，我最早接触是在一个物联网网关项目里。客户要求固件不能被人轻易读出来，就算读出来也跑不了。那时候我才意识到，加密和安全启动不是锦上添花，而是刚需。

这一章我们聊聊固件加密和安全启动。说白了，就是两件事：怎么让固件内容不被看懂，以及怎么确保跑起来的固件是合法的。

15.1 对称加密：AES的实现

对称加密，加密和解密用同一个密钥。速度快，适合嵌入式场景。AES是目前最主流的对称加密算法。

我个人习惯用AES-128-CBC模式。为什么？因为128位密钥在嵌入式MCU上性能足够，CBC模式能抵抗一些模式攻击。

核心要点：AES加密需要处理好密钥存储和IV（初始化向量）。密钥不能硬编码在代码里，IV每次加密要随机生成。

来看一个简单的AES加密示例，基于mbedTLS库：

#include <mbedtls/aes.h>
#include <mbedtls/ctr_drbg.h>

void aes_encrypt_firmware(uint8_t *plaintext, uint32_t len, 
                          uint8_t *key, uint8_t *iv) {
    mbedtls_aes_context aes;
    uint8_t output[256];
    
    mbedtls_aes_init(&aes);
    mbedtls_aes_setkey_enc(&aes, key, 128);
    
    // CBC模式加密
    mbedtls_aes_crypt_cbc(&aes, MBEDTLS_AES_ENCRYPT, 
                          len, iv, plaintext, output);
    
    mbedtls_aes_free(&aes);
}

我在项目中遇到过一个问题：MCU的Flash读取速度跟不上AES解密速度。后来用了DMA配合硬件AES加速器才解决。你想想看，如果解密比读取还慢，启动时间就会变长。

避坑指南：我曾经把AES密钥直接写在固件里，结果被客户用JTAG读出来了。后来改用OTP（一次性可编程）区域存储密钥，或者用芯片的唯一ID派生密钥。

15.2 非对称加密：RSA与ECC基础

非对称加密，公钥加密私钥解密，或者私钥签名公钥验签。RSA和ECC是两种主流算法。

RSA基于大整数分解难题，密钥越长越安全。2048位是当前推荐的最低标准。但RSA在嵌入式上有个问题——计算量大，签名验证慢。

ECC（椭圆曲线密码学）用更短的密钥达到相同安全级别。256位ECC ≈ 3072位RSA。我更喜欢ECC，尤其在资源受限的MCU上。

算法 密钥长度 安全级别 嵌入式适用性
RSA 2048位 112位 中等，需要大内存
ECC 256位 128位 高，适合MCU
RSA 4096位 128位 低，计算开销大

为什么非对称加密在安全启动里这么重要？因为你可以把公钥放在Bootloader里，私钥留在开发环境。这样就算固件被破解，也拿不到私钥。

我建议用ECC做签名验证。256位的ECC签名长度只有64字节，而RSA-2048签名是256字节。对于Flash空间紧张的MCU，这个差距很明显。

15.3 安全启动链设计

安全启动链，说白了就是「信任链」。从最底层的Bootloader开始，一级验证一级，直到应用程序。

典型的启动链是这样的：

  1. ROM Bootloader（芯片出厂固化）验证Flash中的Bootloader
  2. Bootloader验证固件头部的签名
  3. 固件运行后，验证后续的更新包

每一级都只信任上一级验证过的内容。这就是「信任根」的概念。

设计原则：信任链不能有断裂。如果Bootloader不验证固件签名，那前面的加密就白做了。

我参与过一个项目，安全启动链设计如下：

// 伪代码：安全启动验证流程
void secure_boot_chain(void) {
    // 第1步：验证Bootloader自身完整性
    if (!verify_bootloader_hash()) {
        enter_recovery_mode();
        return;
    }
    
    // 第2步：验证固件签名（ECC验签）
    if (!verify_firmware_signature()) {
        enter_recovery_mode();
        return;
    }
    
    // 第3步：解密固件（AES解密）
    decrypt_firmware();
    
    // 第4步：跳转到固件入口
    jump_to_firmware();
}

嗯，这里要注意：验签和解密的顺序不能搞反。先验签再解密，否则你解密一个被篡改的固件，浪费算力。

警告：千万不要把私钥放在固件里。我曾经见过有人把RSA私钥放在固件头部的保留字段里，那等于把家门钥匙放在门口垫子下面。

15.4 实际部署中的坑

安全启动看着简单，实际部署时坑不少。我列几个常见的：

  • 密钥管理混乱：开发密钥、测试密钥、生产密钥混用。建议用HSM（硬件安全模块）管理生产密钥。
  • 回滚攻击：攻击者刷回旧版本固件，利用已知漏洞。解决办法是在固件头加版本号，Bootloader检查版本不能低于当前版本。
  • 调试接口没关：JTAG/SWD接口开着，攻击者直接读Flash。量产时一定要熔断调试接口。

我记得有一次，客户说安全启动验证通过了但固件跑不起来。查了半天，发现是AES解密后的固件加载地址不对。解密后的固件要放到正确的RAM或Flash地址，不然CPU跳转过去就是乱码。

个人经验：调试安全启动时，先不要加密，只做签名验证。等签名验证稳定了，再加解密。这样出问题容易定位。

最后说一句：安全启动不是万能药。它只能保证固件的完整性和来源可信。如果芯片本身有硬件漏洞，或者密钥被物理提取，安全启动也挡不住。但话说回来，对于绝大多数嵌入式产品，做好AES加密+ECC签名验证，已经能挡住99%的攻击者了。
