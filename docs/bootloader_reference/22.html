22、低功耗模式：MCU低功耗模式介绍、Bootloader在低功耗下的行为、唤醒源管理

各位同学，今天我们来聊聊低功耗模式。说实话，这个主题在Bootloader开发里经常被忽略。很多人觉得Bootloader就是个启动加载器，跟低功耗有什么关系？

我在做物联网项目时吃过这个亏。产品做完了，功耗测试死活过不去。查了三天，最后发现是Bootloader在休眠后偷偷把外设时钟全开了。嗯，从那以后，我对低功耗下的Bootloader行为就格外上心。

22.1 MCU低功耗模式介绍

先说说MCU的低功耗模式。不同厂家的叫法不一样，但本质差不多。我以STM32为例，它有三种睡眠模式：

模式 唤醒时间 功耗 CPU状态 外设状态
Sleep模式 几微秒 中等 停止 保持
Stop模式 几十微秒 低 停止 可配置
Standby模式 几毫秒 极低 掉电 掉电

你想想看，这三种模式的区别说白了就是「保留了多少状态」。Sleep模式只是停了CPU时钟，外设还在跑。Standby模式几乎把整个芯片都关了，只留几个唤醒引脚。

关键点：Bootloader通常运行在Standby模式下会有麻烦。因为RAM内容全丢了，重新唤醒后跟冷启动没区别。我个人习惯在Bootloader里尽量避免进入Standby，除非你做好了完整的状态保存机制。

22.2 Bootloader在低功耗下的行为

Bootloader在低功耗下该做什么？这个问题我琢磨了很久。说白了，Bootloader在低功耗场景下要处理三个核心问题：

  1. 要不要响应唤醒？ - 有些唤醒源需要Bootloader处理，比如远程升级请求
  2. 怎么判断是正常唤醒还是异常唤醒？ - 我遇到过电源抖动导致的误唤醒，Bootloader得能识别
  3. 唤醒后要不要跳转到App？ - 还是继续留在Bootloader里等命令

我给大家看一段实际项目中的代码片段。这是我在一个低功耗传感器节点上用的Bootloader唤醒处理逻辑：

void Bootloader_WakeupHandler(void)
{
    uint32_t wakeup_source;
    
    // 读取唤醒源寄存器
    wakeup_source = RCC->CSR & RCC_CSR_WUWF;
    
    // 清除唤醒标志
    RCC->CSR |= RCC_CSR_RMVF;
    
    // 判断唤醒原因
    if (wakeup_source & WAKEUP_SOURCE_RTC)
    {
        // RTC定时唤醒，正常进入App
        JumpToApplication();
    }
    else if (wakeup_source & WAKEUP_SOURCE_GPIO)
    {
        // GPIO唤醒，可能是外部触发
        // 检查是否是升级请求
        if (CheckUpdateRequest())
        {
            // 留在Bootloader等待升级
            WaitForFirmwareUpdate();
        }
        else
        {
            // 正常唤醒，跳转App
            JumpToApplication();
        }
    }
    else
    {
        // 未知唤醒源，安全起见重新进入休眠
        // 我曾经遇到过电源毛刺导致的误唤醒
        // 这里做个计数保护，连续误唤醒3次就复位
        static uint8_t err_count = 0;
        err_count++;
        if (err_count > 3)
        {
            NVIC_SystemReset();
        }
        EnterLowPowerMode();
    }
}

个人经验：这段代码里的误唤醒保护是我踩坑后加的。有一次客户现场，设备频繁唤醒又休眠，功耗直接翻了三倍。查到最后发现是电源纹波触发了GPIO中断。加了计数保护后，问题就解决了。

22.3 唤醒源管理

唤醒源管理，说白了就是「谁有资格把MCU叫醒」。常见的唤醒源有：

  • RTC闹钟 - 定时唤醒，最常用
  • GPIO外部中断 - 按键、传感器触发
  • 比较器输出 - 模拟信号触发
  • USB唤醒 - 插USB时唤醒
  • 以太网唤醒 - 网络数据包唤醒

我建议在Bootloader里做一个统一的唤醒源管理模块。为什么？因为不同唤醒源的处理优先级不一样。举个例子：

唤醒源 优先级 Bootloader处理方式
RTC闹钟 低 直接跳转App
GPIO（升级引脚） 高 进入升级模式
USB插入 中 检查是否有升级命令
看门狗复位 紧急 记录错误，重新初始化

这里有个坑要注意。唤醒源的优先级判断不能放在中断服务函数里做。为什么？因为中断服务函数里执行时间太长，会影响系统响应。我一般是在主循环里处理唤醒源判断：

void main(void)
{
    // 初始化
    SystemInit();
    
    // 检查是否是唤醒复位
    if (IsWakeupReset())
    {
        // 处理唤醒源
        WakeupSource_t src = GetWakeupSource();
        HandleWakeupSource(src);
    }
    else
    {
        // 正常上电启动
        NormalBoot();
    }
    
    // 主循环
    while(1)
    {
        // 处理低功耗相关任务
        ProcessLowPowerTasks();
    }
}

警告：千万不要在中断里调用延时函数或者复杂的外设操作。我见过有人直接在RTC中断里做Flash擦写，结果系统卡死。中断服务函数要快进快出，复杂逻辑放到主循环里做。

22.4 低功耗模式下的固件升级策略

最后聊聊低功耗模式下的固件升级。这是个很实际的问题。设备在休眠，你怎么升级？

我个人常用的方案有两种：

  1. 定时唤醒检查 - 设备每隔一段时间唤醒，检查是否有升级包。适合对实时性要求不高的场景。
  2. 外部触发唤醒 - 通过GPIO或特定协议唤醒设备，然后开始升级。适合需要即时升级的场景。

我做过一个项目，设备装在野外，一年换一次电池。固件升级全靠RTC定时唤醒。每天凌晨3点唤醒一次，检查服务器有没有新固件。有就下载，没有继续睡。这个方案功耗控制得很好，一节电池撑了两年。

核心建议：低功耗下的Bootloader设计，核心就一句话——「该睡就睡，该醒就醒，醒了别磨蹭」。把唤醒源管理好，把升级流程做精简，你的Bootloader在低功耗场景下就能跑得很稳。
