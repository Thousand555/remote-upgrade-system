第27章 RTOS集成：FreeRTOS在Bootloader中的应用、任务调度与优先级设计、互斥与同步

说实话，很多人觉得Bootloader就是个简单的搬运工——把固件从Flash搬到内存，然后跳转执行。但我在实际项目中遇到过几次棘手的情况：比如OTA升级时，一边要擦写Flash，一边还要响应外部命令；又比如多核芯片启动时，不同核心需要协同工作。这时候，一个裸奔的Bootloader就显得力不从心了。

嗯，这就是为什么我们要把FreeRTOS请进Bootloader。你想想看，有了RTOS，Bootloader就不再是单线程的傻小子，而是一个能同时处理多任务的“小系统”。

27.1 为什么Bootloader需要RTOS？

我刚开始做Bootloader时，也觉得加RTOS是杀鸡用牛刀。直到有一次，客户要求在升级过程中不能中断通信——一边收数据包，一边擦写Flash，还得实时反馈进度。裸机下用状态机硬扛，代码写得跟意大利面条似的。

RTOS带来的核心好处有三个：

  • 任务隔离：每个功能模块独立成任务，互不干扰
  • 实时响应：高优先级任务能抢占CPU，保证关键操作不被耽误
  • 资源管理：通过信号量、队列等机制，避免资源竞争

说白了，RTOS让Bootloader从“一个人干所有事”变成了“一个团队分工协作”。

我的经验：在STM32H7上做Bootloader时，我用了FreeRTOS。升级过程中，一个任务负责接收数据包，一个任务负责擦写Flash，还有一个任务负责心跳LED。三个任务各司其职，代码清晰多了。

27.2 FreeRTOS在Bootloader中的裁剪与配置

Bootloader的资源通常很紧张——RAM可能只有几十KB，Flash也有限。所以FreeRTOS不能全功能搬进来，得做裁剪。

我个人习惯这样配置：

  • 任务数量：3-5个就够，别贪多
  • 堆大小：根据任务栈总和，再加20%余量
  • 时钟节拍：1000Hz（1ms）够用，别设太高浪费CPU
  • 关闭不用的功能：比如软件定时器、事件组，用不到就关掉

下面是一个典型的FreeRTOS配置示例：

// FreeRTOSConfig.h 裁剪配置
#define configUSE_PREEMPTION          1
#define configUSE_IDLE_HOOK           0
#define configUSE_TICK_HOOK           0
#define configCPU_CLOCK_HZ            ((uint32_t)216000000)
#define configTICK_RATE_HZ            ((TickType_t)1000)
#define configMAX_PRIORITIES          5
#define configMINIMAL_STACK_SIZE      ((uint16_t)128)
#define configTOTAL_HEAP_SIZE         ((size_t)(8 * 1024))  // 8KB堆
#define configMAX_TASK_NAME_LEN       8
#define configUSE_TRACE_FACILITY      0
#define configUSE_STATS_FORMATTING_FUNCTIONS 0
#define configUSE_CO_ROUTINES         0
#define configUSE_MUTEXES             1
#define configUSE_QUEUE_SYNC          1
#define configUSE_COUNTING_SEMAPHORES 1

避坑指南：我曾经把堆设得太小，结果任务创建失败，查了半天才发现是堆不够。建议先估算每个任务的栈大小，再乘以任务数，最后加30%余量。

27.3 任务调度与优先级设计

任务优先级设计是门学问。优先级设高了，低优先级任务可能饿死；设低了，关键操作可能被耽误。

在Bootloader中，我通常这样划分优先级：

优先级 任务名称 功能描述
4（最高） 通信任务 处理UART/USB/CAN数据收发
3 Flash操作任务 擦除、编程、校验
2 命令解析任务 解析上位机指令，调度其他任务
1 状态上报任务 定期上报升级进度、状态
0（最低） 空闲任务 系统空闲时运行，比如喂狗

为什么会这样设计？因为通信任务必须第一时间响应，否则数据包会丢失。Flash操作虽然重要，但可以稍微等一下——毕竟擦写Flash本身就很慢，不差那几毫秒。

任务创建代码示例：

void Bootloader_TaskCreate(void)
{
    BaseType_t xReturn = pdPASS;
    
    // 创建通信任务 - 最高优先级
    xReturn = xTaskCreate(
        Task_Communication,     // 任务函数
        "Comm",                 // 任务名称
        256,                    // 栈大小（字）
        NULL,                   // 参数
        4,                      // 优先级
        NULL                    // 任务句柄
    );
    
    // 创建Flash操作任务
    xReturn = xTaskCreate(
        Task_FlashOperation,
        "Flash",
        512,                    // Flash操作需要较大栈
        NULL,
        3,
        NULL
    );
    
    // 创建命令解析任务
    xReturn = xTaskCreate(
        Task_CommandParser,
        "Cmd",
        256,
        NULL,
        2,
        NULL
    );
    
    // 启动调度器
    vTaskStartScheduler();
}

注意：Flash操作任务的栈要设大一些，因为擦写Flash时可能会调用较深的函数栈。我遇到过栈溢出导致系统崩溃的情况，后来把栈从256改成512才解决。

27.4 互斥与同步机制

多任务环境下，资源竞争是绕不开的问题。比如通信任务收到了数据，要写入一个缓冲区，而Flash操作任务正从同一个缓冲区读取数据——这就冲突了。

FreeRTOS提供了几种同步机制，我挑几个常用的说说：

27.4.1 互斥量（Mutex）保护共享资源

互斥量说白了就是一把锁。谁拿到锁，谁就能访问共享资源。我用得最多的是保护Flash操作缓冲区：

// 定义互斥量句柄
SemaphoreHandle_t xFlashMutex;

// 初始化互斥量
xFlashMutex = xSemaphoreCreateMutex();

// 通信任务写入数据
void Task_Communication(void *pvParameters)
{
    uint8_t dataBuffer[256];
    
    while(1)
    {
        // 接收数据
        if(ReceiveData(dataBuffer, sizeof(dataBuffer)))
        {
            // 获取互斥量
            if(xSemaphoreTake(xFlashMutex, portMAX_DELAY) == pdTRUE)
            {
                // 将数据写入共享缓冲区
                WriteToSharedBuffer(dataBuffer);
                
                // 释放互斥量
                xSemaphoreGive(xFlashMutex);
            }
        }
    }
}

// Flash操作任务读取数据
void Task_FlashOperation(void *pvParameters)
{
    uint8_t dataBuffer[256];
    
    while(1)
    {
        // 等待数据到达的信号
        if(xSemaphoreTake(xDataAvailable, portMAX_DELAY) == pdTRUE)
        {
            // 获取互斥量
            if(xSemaphoreTake(xFlashMutex, portMAX_DELAY) == pdTRUE)
            {
                // 从共享缓冲区读取数据
                ReadFromSharedBuffer(dataBuffer);
                
                // 释放互斥量
                xSemaphoreGive(xFlashMutex);
                
                // 写入Flash
                WriteToFlash(dataBuffer);
            }
        }
    }
}

我的经验：互斥量一定要成对使用——Take和Give必须配对。我曾经在某个分支里忘了Give，结果其他任务永远拿不到锁，整个系统卡死了。后来我习惯用宏封装Take和Give，减少出错概率。

27.4.2 信号量实现任务同步

信号量更像是一个“通知机制”。比如通信任务收完一包数据后，通知Flash操作任务开始处理：

// 定义二值信号量
SemaphoreHandle_t xDataAvailable;

// 初始化
xDataAvailable = xSemaphoreCreateBinary();

// 通信任务 - 通知Flash任务
void Task_Communication(void *pvParameters)
{
    while(1)
    {
        if(ReceivePacket())
        {
            // 发送信号量，通知Flash任务
            xSemaphoreGive(xDataAvailable);
        }
    }
}

// Flash任务 - 等待通知
void Task_FlashOperation(void *pvParameters)
{
    while(1)
    {
        // 等待信号量，阻塞等待
        if(xSemaphoreTake(xDataAvailable, portMAX_DELAY) == pdTRUE)
        {
            // 收到通知，开始处理数据
            ProcessAndWriteFlash();
        }
    }
}

你想想看，如果没有信号量，Flash任务就得轮询检查有没有新数据——浪费CPU不说，还容易漏掉数据。用信号量就优雅多了，任务在等待时处于阻塞状态，不占CPU。

27.4.3 队列传递数据

如果只是传递少量数据，队列比互斥量+共享缓冲区更方便：

// 定义队列句柄
QueueHandle_t xDataQueue;

// 初始化队列，每个元素256字节，深度10
xDataQueue = xQueueCreate(10, 256);

// 通信任务发送数据
void Task_Communication(void *pvParameters)
{
    uint8_t data[256];
    
    while(1)
    {
        if(ReceiveData(data, sizeof(data)))
        {
            // 发送到队列
            if(xQueueSend(xDataQueue, data, 0) != pdPASS)
            {
                // 队列满了，丢弃数据
                LogError("Queue full, data lost");
            }
        }
    }
}

// Flash任务接收数据
void Task_FlashOperation(void *pvParameters)
{
    uint8_t data[256];
    
    while(1)
    {
        // 从队列接收，阻塞等待
        if(xQueueReceive(xDataQueue, data, portMAX_DELAY) == pdPASS)
        {
            WriteToFlash(data);
        }
    }
}

避坑指南：我曾经在中断服务函数里直接调用xQueueSend，结果系统崩溃了。后来才想起来，中断里要用xQueueSendFromISR。记住：带FromISR后缀的API才是中断安全的。

27.5 实际项目中的注意事项

把FreeRTOS集成到Bootloader里，有几个坑我踩过，分享给你：

  • 中断优先级：FreeRTOS要求中断优先级不能高于configMAX_SYSCALL_INTERRUPT_PRIORITY，否则系统API不能正常工作。我习惯把所有中断优先级设成5（数值越大优先级越低），省得麻烦。
  • 栈溢出检测：开启configCHECK_FOR_STACK_OVERFLOW，配合vApplicationStackOverflowHook回调函数，能帮你快速定位栈溢出问题。
  • 看门狗处理：在空闲任务里喂狗比较安全。别在通信任务里喂，万一通信卡住了，看门狗也救不了你。
  • 跳转到APP前的清理：在跳转到用户应用程序之前，记得调用vTaskEndScheduler()停止调度器，然后关闭所有中断，最后复位外设。否则APP启动时可能会因为RTOS残留状态而出问题。

嗯，关于FreeRTOS在Bootloader中的应用，今天就聊这么多。说白了，RTOS让Bootloader变得更灵活、更可靠，但也带来了额外的复杂性和资源开销。要不要用，取决于你的项目需求——如果只是简单的串口升级，裸机就够了；但如果要处理多任务、实时响应，FreeRTOS绝对值得一试。
