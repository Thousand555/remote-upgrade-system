11、固件校验与完整性检查：CRC校验实现、SHA256哈希校验、签名验证流程

各位同学，今天我们来聊聊Bootloader里一个绕不开的话题——固件校验。

说白了，就是你怎么确保你下载到芯片里的固件是完整的、没被篡改过的。我刚开始做Bootloader那会儿，觉得这步可有可无，直到有一次现场升级把设备刷成砖了……嗯，从那以后我再也不敢跳过校验了。

11.1 为什么需要固件校验？

你想想看，固件在传输过程中可能被干扰，存储介质也可能有坏块。更严重的是，如果有人恶意篡改了固件，你的设备可能就被植入后门了。

所以，Bootloader在跳转到新固件之前，必须做三件事：

  • 完整性检查：固件有没有被损坏？
  • 一致性检查：固件是不是完整下载了？
  • 合法性检查：固件是不是来自可信的发布方？

这三个问题，分别对应我们今天要讲的三种技术：CRC、SHA256、签名验证。

11.2 CRC校验：轻量级的完整性守护者

CRC（循环冗余校验）是我个人最喜欢用的快速校验方式。它计算量小，硬件支持好，适合在资源受限的嵌入式系统里用。

CRC的原理不复杂：把数据看作一个巨大的二进制数，然后用一个固定的多项式去除，余数就是CRC值。接收方用同样的多项式再算一遍，如果余数相同，说明数据没变。

我在项目中遇到过一个问题：CRC多项式选错了，导致校验总是失败。后来发现，不同的CRC标准（CRC-16、CRC-32、CRC-CCITT）用的多项式不一样，千万别搞混。

常用CRC标准速查表

标准 多项式 宽度 典型应用
CRC-8 0x07 8位 1-Wire总线
CRC-16-IBM 0x8005 16位 Modbus协议
CRC-32 0x04C11DB7 32位 以太网、ZIP文件
CRC-CCITT 0x1021 16位 XMODEM、蓝牙

下面是一个CRC-32的软件实现示例，我习惯用查表法，速度比逐位计算快很多：

// CRC-32查表法实现
static uint32_t crc32_table[256];

void crc32_init_table(void) {
    for (uint32_t i = 0; i < 256; i++) {
        uint32_t crc = i;
        for (int j = 0; j < 8; j++) {
            if (crc & 1)
                crc = (crc >> 1) ^ 0xEDB88320;
            else
                crc >>= 1;
        }
        crc32_table[i] = crc;
    }
}

uint32_t crc32_calc(uint8_t *data, uint32_t len) {
    uint32_t crc = 0xFFFFFFFF;
    for (uint32_t i = 0; i < len; i++) {
        uint8_t index = (crc ^ data[i]) & 0xFF;
        crc = (crc >> 8) ^ crc32_table[index];
    }
    return crc ^ 0xFFFFFFFF;
}

小技巧：CRC-32的初始值和最终异或值都是0xFFFFFFFF，这是标准做法。如果你发现和别人的CRC算出来不一样，先检查这两个参数。

11.3 SHA256哈希校验：更安全的完整性保证

CRC虽然快，但它有个致命弱点——容易被碰撞。说白了，就是你能故意构造两个不同的数据，算出相同的CRC值。这在安全场景下是不能接受的。

SHA256就不一样了。它是单向哈希函数，输出256位的摘要。哪怕你只改了一个比特，整个摘要都会变得面目全非。而且，从摘要反推原始数据，在计算上是不可行的。

我曾经在一个OTA升级项目里，用CRC校验固件头，用SHA256校验整个固件体。这样既保证了速度，又保证了安全。

SHA256的计算过程比较复杂，我直接给一个常用的实现接口：

// SHA256上下文结构体
typedef struct {
    uint32_t state[8];    // 哈希状态
    uint64_t count;       // 已处理字节数
    uint8_t  buffer[64];  // 数据缓冲区
} SHA256_CTX;

// 接口函数
void sha256_init(SHA256_CTX *ctx);
void sha256_update(SHA256_CTX *ctx, uint8_t *data, uint32_t len);
void sha256_final(SHA256_CTX *ctx, uint8_t hash[32]);

使用起来很简单：

uint8_t firmware_hash[32];
SHA256_CTX ctx;

sha256_init(&ctx);
sha256_update(&ctx, firmware_data, firmware_size);
sha256_final(&ctx, firmware_hash);

// 比较计算出的hash和固件头中存储的hash
if (memcmp(firmware_hash, expected_hash, 32) == 0) {
    // 校验通过
} else {
    // 固件损坏，拒绝启动
}

注意：SHA256的计算量比CRC大得多。在低主频的MCU上，校验一个几MB的固件可能需要好几秒。我建议在Bootloader里用DMA加速，或者只在关键区域做哈希校验。

11.4 签名验证流程：确保固件来源可信

CRC和SHA256只能保证固件没被损坏，但保证不了固件是谁写的。如果有人伪造了一个固件，算好了正确的哈希值，你的设备照样会认。

这时候就需要签名验证了。签名验证用的是非对称加密算法，比如RSA或ECDSA。流程是这样的：

  1. 签名阶段（在PC端完成）：
    • 计算固件的SHA256哈希值
    • 用私钥对哈希值进行加密，生成签名
    • 将签名附加到固件末尾
  2. 验证阶段（在Bootloader中完成）：
    • 计算固件的SHA256哈希值
    • 用公钥解密签名，得到原始哈希值
    • 比较两个哈希值是否一致

嗯，这里要注意：公钥是硬编码在Bootloader里的，私钥要严格保管。我见过一个项目，私钥被提交到了Git仓库里……那场面，简直是灾难。

下面是一个简化的RSA签名验证流程：

// 签名验证流程（伪代码）
int verify_firmware_signature(uint8_t *firmware, uint32_t size) {
    uint8_t hash[32];
    uint8_t decrypted_hash[32];
    
    // 1. 计算固件哈希
    sha256_calc(firmware, size - SIGNATURE_SIZE, hash);
    
    // 2. 提取签名（固件末尾）
    uint8_t *signature = firmware + size - SIGNATURE_SIZE;
    
    // 3. 用公钥解密签名
    rsa_public_decrypt(signature, SIGNATURE_SIZE, decrypted_hash, public_key);
    
    // 4. 比较哈希值
    if (memcmp(hash, decrypted_hash, 32) == 0) {
        return 1;  // 验证通过
    }
    return 0;  // 验证失败
}

关键点：签名验证的强度取决于密钥长度和算法选择。我个人建议：

  • RSA至少用2048位，ECDSA用P-256曲线
  • 公钥要写在Bootloader的只读区域，防止被篡改
  • 签名验证失败时，Bootloader绝对不能跳转到固件

11.5 三种校验方式的对比与选择

说了这么多，到底该用哪种？我根据自己的经验，给一个参考：

校验方式 安全性 计算速度 资源消耗 适用场景
CRC 低（易碰撞） 极快 极低 传输校验、快速检查
SHA256 高（无碰撞） 中等 中等 完整性验证
签名验证 极高（防篡改） 慢 高 安全启动、OTA升级

在实际项目中，我通常这样组合：

  • 普通产品：CRC校验固件头 + SHA256校验固件体
  • 安全产品：SHA256 + RSA/ECDSA签名验证
  • 高性能场景：硬件CRC + 硬件SHA加速 + 签名验证

避坑指南：我曾经在一个项目里只用了CRC校验，结果被攻击者用CRC碰撞绕过了。从那以后，凡是涉及OTA升级的，我至少会用SHA256。签名验证虽然慢，但它是最后一道防线，值得花那几秒钟。

11.6 总结

固件校验是Bootloader的看门狗，它决定了你的设备会不会被恶意固件攻破。CRC是轻骑兵，SHA256是正规军，签名验证是特种部队——各有各的用处，关键是要搭配得当。

最后提醒一句：校验逻辑一定要写在Bootloader里，而且要在跳转到固件之前执行。如果等固件跑起来了再校验，那就晚了。
