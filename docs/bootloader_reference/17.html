17、Bootloader与APP交互：共享内存设计、标志位通信机制、系统状态机设计

好，咱们今天聊一个非常实战的话题——Bootloader和APP之间怎么“说话”。

很多新手朋友觉得，Bootloader把APP加载到内存里，跳转过去就完事了。其实远没那么简单。我做过好几个量产项目，踩过最大的坑就是：Bootloader和APP各干各的，互不搭理，结果升级失败时连个错误原因都查不到。

说白了，这两个程序虽然跑在不同的地址空间，但它们共享同一颗芯片、同一片RAM。怎么利用好这片共享区域，就是本节的核心。

17.1 共享内存设计：给两个程序搭一座桥

先问一个问题：Bootloader和APP怎么交换数据？

答案很简单——用RAM。但要注意，不是随便找块内存就能用。我见过有人直接在APP的全局变量里写数据，Bootloader跳转后变量值全丢了。为什么？因为APP启动时会把BSS段清零，你的数据早没了。

所以，共享内存必须满足两个条件：

  • 地址固定：不能依赖链接器自动分配，要手动指定地址
  • 不被初始化：Bootloader和APP都不能对它做清零操作

我个人习惯的做法是：在链接脚本里预留一块区域，比如从RAM末尾往前划出256字节。

以STM32为例，在链接脚本中这样定义：

/* 在链接脚本中定义共享内存区域 */
.shared_mem (NOLOAD) : {
    . = ALIGN(4);
    _shared_mem_start = .;
    *(.shared_section)
    . = ALIGN(4);
    _shared_mem_end = .;
} > RAM

然后在C代码里，用__attribute__指定段：

#define SHARED_MEM __attribute__((section(".shared_section")))

typedef struct {
    uint32_t magic;          // 魔数，验证共享内存是否有效
    uint32_t boot_flag;      // 启动标志
    uint32_t update_status;  // 升级状态
    uint32_t error_code;     // 错误码
    uint8_t  reserved[240];  // 预留空间
} SharedMemory_t;

volatile SharedMemory_t g_shared_mem SHARED_MEM;

注意：一定要加 volatile 关键字！编译器优化可能会把共享变量的读写给优化掉，我吃过这个亏，查了两天才发现是编译器把循环里的变量读取给优化没了。

17.2 标志位通信机制：用约定好的暗号说话

共享内存有了，接下来就是怎么用。我习惯用一套“标志位+魔数”的通信机制。

魔数（Magic Number）：这是第一道防线。Bootloader启动时先检查共享内存里的魔数是不是预设值（比如0xA5A5A5A5）。如果不是，说明共享内存无效，可能是第一次上电或者APP没写数据。

启动标志（Boot Flag）：告诉Bootloader下一步该干什么。

标志值 含义 谁设置的
0x00 正常启动APP Bootloader默认
0x01 进入固件升级模式 APP收到升级指令后设置
0x02 回滚到备份固件 APP检测到固件损坏
0xFF 强制恢复出厂 用户按键触发

代码实现起来很直接：

// APP端：收到升级指令后设置标志
void app_request_update(void)
{
    g_shared_mem.magic = 0xA5A5A5A5;
    g_shared_mem.boot_flag = 0x01;
    g_shared_mem.update_status = 0;
    
    // 然后执行软复位
    NVIC_SystemReset();
}

// Bootloader端：启动时检查
void bootloader_main(void)
{
    if (g_shared_mem.magic != 0xA5A5A5A5) {
        // 共享内存无效，直接启动APP
        jump_to_app();
        return;
    }
    
    switch (g_shared_mem.boot_flag) {
        case 0x01:
            // 进入升级模式
            enter_update_mode();
            break;
        case 0x02:
            // 回滚固件
            rollback_firmware();
            break;
        default:
            // 正常启动
            jump_to_app();
            break;
    }
    
    // 启动APP前清除标志，防止下次误判
    g_shared_mem.magic = 0;
    g_shared_mem.boot_flag = 0;
}

我的经验：设置标志后一定要清空再跳转。我曾经遇到一个bug：APP崩溃后自动复位，Bootloader看到标志位还在，又进升级模式，结果死循环了。后来我改成“跳转前清标志，APP启动后再重新设置”。

17.3 系统状态机设计：让升级过程有章可循

光有标志位还不够，升级过程本身就是一个状态机。我习惯把状态定义在共享内存里，这样Bootloader和APP都能看到当前进度。

typedef enum {
    STATE_IDLE          = 0,  // 空闲
    STATE_CHECKING      = 1,  // 检查固件合法性
    STATE_DOWNLOADING   = 2,  // 正在下载
    STATE_VERIFYING     = 3,  // 校验固件
    STATE_FLASHING      = 4,  // 写入Flash
    STATE_COMPLETE      = 5,  // 升级完成
    STATE_ERROR         = 6   // 出错
} UpdateState_t;

这个状态机怎么用？举个例子：

  • APP收到升级包后，把状态设为STATE_DOWNLOADING
  • 每收到一包数据，更新进度百分比（存在reserved数组里）
  • 下载完成，状态切到STATE_VERIFYING
  • 校验通过，切到STATE_FLASHING
  • 全部写完，切到STATE_COMPLETE，然后复位

Bootloader启动时看到STATE_COMPLETE，就知道升级成功了，直接启动新APP。

如果中途断电呢？Bootloader启动时看到STATE_DOWNLOADING或STATE_FLASHING，就知道上次升级没完成，可以自动进入恢复模式。

核心思想：状态机让升级过程变得可追溯、可恢复。哪怕掉电了，下次启动也能知道卡在哪一步。

17.4 避坑指南：我踩过的几个雷

讲到这里，分享几个实战中遇到的坑：

  1. Cache一致性问题：如果你用的芯片有D-Cache，共享内存区域要配置成非缓存（Non-cacheable）。否则Bootloader写的数据，APP读到的可能是Cache里的旧值。我曾在STM32H7上被这个问题折磨了一周。
  2. 中断向量表冲突：共享内存的地址不要和中断向量表重叠。有些芯片的中断向量表可以重映射，但默认位置通常在Flash起始地址，和RAM不冲突。但如果你用了TCM或紧耦合内存，要特别小心。
  3. 看门狗干扰：升级过程中如果看门狗超时复位，共享内存里的数据可能被部分修改。我建议在进入升级模式后，把看门狗喂狗周期调长，或者干脆在关键步骤暂停看门狗。
  4. 多核芯片的共享问题：如果是双核MCU，两个核共享同一片RAM，要加互斥机制。最简单的做法是用原子操作，或者硬件信号量。

嗯，差不多就这些。共享内存设计看似简单，但细节决定成败。你想想看，一个升级失败的产品，如果连失败原因都查不到，用户会怎么想？所以，花点时间把这块做好，绝对值得。
