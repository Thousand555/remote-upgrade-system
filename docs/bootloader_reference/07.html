7、Flash驱动开发：Flash存储器特性、Flash读/写/擦除操作、Flash驱动分层设计

好，咱们今天聊聊Flash驱动。这玩意儿，说简单也简单，说复杂，它真能把你折腾得够呛。我在做Bootloader那几年，跟Flash打交道的时间，比跟我老婆说话的时间都多。你想想看，Bootloader的命根子就是Flash，代码存里头，参数存里头，升级也得靠它。要是驱动没写好，板子一上电就成砖，那可就尴尬了。

7.1 Flash存储器特性——你得先懂它的脾气

Flash不是RAM，你不能想怎么读写就怎么读写。它有自己的一套规矩。我个人习惯，在动笔写驱动之前，先花半小时把芯片手册里Flash那章翻烂。为什么？因为不同厂商、不同型号的Flash，特性差异很大。

先说说几个核心特性：

  • 非易失性：断电不丢数据，这是它存在的意义。
  • 按扇区/块擦除：这是最要命的特性。你不能像写SRAM那样，直接往一个地址写个新值就把旧值覆盖了。不行！你得先把整个扇区擦干净（变成全1，通常是0xFF），然后再写。我遇到过新手，直接往Flash里写数据，结果读出来全是乱的，就是因为没擦除。
  • 擦写次数有限：一般是10万次左右。虽然听起来很多，但如果你在循环里反复擦写同一个扇区，用不了多久就废了。这就是所谓的“磨损”。
  • 编程（写）操作：通常只能把1写成0，不能把0写成1。把0变成1的唯一办法就是擦除。所以，擦除操作是把整个扇区恢复成全1。
  • 读操作：这个相对简单，跟读RAM差不多，直接寻址就行。但要注意，有些Flash在读取时需要配置等待周期（Wait State），特别是当主频比较高的时候。

重要： 写Flash之前，一定要先确认目标地址所在的扇区是否已经被擦除过。如果没有，必须先擦除。这是Flash驱动开发的第一条铁律。

我曾经在一个项目里，为了省时间，跳过了擦除检查。结果呢？固件升级到一半，系统挂了。因为新数据写到了没擦干净的旧数据上，校验通不过，整个板子变砖。最后只能拿JTAG出来救砖，那叫一个狼狈。

7.2 Flash读/写/擦除操作——三板斧

好，特性了解了，咱们来看看具体怎么操作。这三板斧，你得练得滚瓜烂熟。

7.2.1 读操作

读操作最简单。大部分MCU的Flash都是映射到统一的地址空间里的。你直接定义一个指针，指向那个地址，然后取值就行了。

// 从Flash地址读取一个32位数据
uint32_t Flash_ReadWord(uint32_t addr) {
    return *(volatile uint32_t *)addr;
}

// 从Flash地址读取一段数据到RAM缓冲区
void Flash_ReadBuffer(uint32_t addr, uint32_t *buf, uint32_t len) {
    for (uint32_t i = 0; i < len; i++) {
        buf[i] = *(volatile uint32_t *)(addr + i * 4);
    }
}

嗯，这里要注意，一定要用 volatile 关键字。为什么？因为编译器可能会优化，觉得这个地址的值没变过，就直接从寄存器里取了。加了 volatile，就是告诉编译器：“每次读都老老实实去内存里取，别给我耍小聪明。”

7.2.2 写操作（编程）

写操作就麻烦一些了。你得按照芯片手册里的“编程流程”来。一般步骤是：

  1. 解锁Flash控制寄存器（防止误操作）。
  2. 设置编程模式。
  3. 写入数据。
  4. 等待编程完成（轮询状态寄存器或等待中断）。
  5. 锁定Flash控制寄存器。

以某款常见的Cortex-M MCU为例，它的Flash编程流程大概是这样的：

void Flash_ProgramWord(uint32_t addr, uint32_t data) {
    // 1. 解锁
    while (FLASH->SR & FLASH_SR_BSY); // 等待上一次操作完成
    FLASH->KEYR = 0x45670123;
    FLASH->KEYR = 0xCDEF89AB;

    // 2. 设置编程宽度（这里假设是32位）
    FLASH->CR |= FLASH_CR_PG;

    // 3. 写入数据（这个写操作会触发编程）
    *(volatile uint32_t *)addr = data;

    // 4. 等待完成
    while (FLASH->SR & FLASH_SR_BSY);

    // 5. 检查错误
    if (FLASH->SR & FLASH_SR_PGERR) {
        // 处理编程错误
    }

    // 6. 锁定
    FLASH->CR &= ~FLASH_CR_PG;
    FLASH->CR |= FLASH_CR_LOCK;
}

小技巧： 写操作时，最好关掉全局中断。因为Flash编程是个比较慢的过程，如果中间来了个中断，中断服务程序里又去访问Flash，很容易出问题。我一般会在编程前调用 __disable_irq()，编程完再 __enable_irq()。

7.2.3 擦除操作

擦除操作跟编程类似，但更耗时。一个扇区擦除，可能要几十毫秒甚至上百毫秒。流程如下：

  1. 解锁。
  2. 设置扇区擦除模式。
  3. 指定要擦除的扇区号。
  4. 开始擦除（通常是通过设置一个触发位）。
  5. 等待擦除完成。
  6. 锁定。
void Flash_EraseSector(uint32_t sector_num) {
    // 1. 解锁
    while (FLASH->SR & FLASH_SR_BSY);
    FLASH->KEYR = 0x45670123;
    FLASH->KEYR = 0xCDEF89AB;

    // 2. 设置扇区擦除模式
    FLASH->CR |= FLASH_CR_SER;

    // 3. 选择扇区
    FLASH->CR &= ~FLASH_CR_SNB_MASK;
    FLASH->CR |= (sector_num << FLASH_CR_SNB_POS);

    // 4. 开始擦除
    FLASH->CR |= FLASH_CR_START;

    // 5. 等待完成
    while (FLASH->SR & FLASH_SR_BSY);

    // 6. 锁定
    FLASH->CR &= ~FLASH_CR_SER;
    FLASH->CR |= FLASH_CR_LOCK;
}

警告： 擦除操作是不可逆的！一旦擦除，整个扇区的数据就全没了。所以，在调用擦除函数之前，一定要再三确认扇区号是否正确。我建议在驱动层加一个保护机制，比如只允许擦除特定的、用于存储数据的扇区，禁止擦除存放代码的扇区。

7.3 Flash驱动分层设计——让代码更优雅

好了，底层的读写擦除都会了。但你不能把这些操作直接扔给上层应用去调用。那样代码会乱成一锅粥。我个人习惯，把Flash驱动分成三层：

层次 名称 职责 示例接口
第1层 硬件抽象层 (HAL) 直接操作寄存器，实现最基本的读、写、擦除、锁定/解锁。 HAL_Flash_ReadWord(), HAL_Flash_ProgramWord(), HAL_Flash_EraseSector()
第2层 驱动层 (Driver) 封装HAL层，提供更高级的功能，如按页写入、按区域擦除、校验、磨损均衡等。 Flash_WritePage(), Flash_EraseRegion(), Flash_Verify()
第3层 管理/服务层 (Manager) 面向应用，提供逻辑上的存储服务，如参数存储、固件升级接口、日志记录等。 Param_Save(), Param_Load(), FOTA_WriteFirmware()

为什么要这么分？说白了，就是为了解耦和复用。

  • HAL层：跟具体的MCU型号强相关。换一颗MCU，只需要重写这一层。上面两层基本不用动。
  • 驱动层：跟Flash的物理特性相关，但跟MCU型号无关。比如，你可以在这一层实现一个“先擦除再写入”的原子操作。
  • 管理/服务层：跟业务逻辑相关。比如，Bootloader里的固件升级模块，它只关心“把数据写到Flash的哪个区域”，它不关心底层是怎么擦除、怎么编程的。

我记得有一次，项目中期换了MCU。因为我的Flash驱动是分层设计的，我只花了半天时间就移植好了。而另一个同事，他的驱动是“一锅烩”的，所有逻辑都揉在一起，结果整整折腾了一个星期。从那以后，我们团队就定下了规矩：Flash驱动必须分层。

嗯，最后再啰嗦一句。写Flash驱动，一定要有“容错”意识。比如，在写操作之前，先检查目标地址是不是在Flash范围内；在擦除操作之前，先检查扇区号是不是合法。这些看似多余的检查，往往能在关键时刻救你一命。

好，今天就聊到这儿。下一节，咱们聊聊Flash驱动里更高级的话题——磨损均衡和掉电保护。这些东西在实际产品中非常关键，尤其是那些需要频繁读写参数的系统。
