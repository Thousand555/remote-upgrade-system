第十二章：固件烧录与跳转

好，咱们今天聊点实在的。固件写进去了，怎么让它跑起来？这中间的门道，比你想的要多。

我个人习惯把这一章分成两大部分：一是怎么把固件安全地烧进Flash，二是怎么从Bootloader跳转到应用程序。这两个环节，任何一个出问题，板子就变砖了。嗯，我当年就吃过这个亏。

12.1 固件写入Flash的完整流程

先说说烧录。说白了，就是把你的二进制文件，一个字节一个字节地塞进Flash里。但这里有个坑——Flash不能像RAM那样随便写。

Flash的特性决定了写入方式：

  • 擦除操作：Flash必须先擦除才能写。擦除的最小单位是扇区（Sector），不是字节。
  • 写入操作：擦除后，按页（Page）或按字（Word）写入。
  • 读取操作：这个简单，直接地址访问就行。

我在项目中遇到过一件事：有个同事没做擦除就直接写，结果数据全是乱的。排查了两天才找到原因。你想想看，这种低级错误，其实很容易避免。

核心流程：

  1. 接收固件数据（通过UART、SPI、USB等接口）
  2. 校验数据完整性（CRC32或SHA256）
  3. 擦除目标扇区
  4. 按页写入数据
  5. 读取验证（读回比对）
  6. 标记固件有效标志

代码示例，我习惯这样写Flash写入函数：

// 伪代码：Flash写入流程
int flash_write_firmware(uint32_t addr, uint8_t *data, uint32_t len) {
    uint32_t sector_size = 4096;  // 假设扇区大小4KB
    uint32_t page_size = 256;     // 假设页大小256字节
    
    // 1. 计算需要擦除的扇区范围
    uint32_t start_sector = addr / sector_size;
    uint32_t end_sector = (addr + len) / sector_size;
    
    // 2. 逐个扇区擦除
    for (uint32_t i = start_sector; i <= end_sector; i++) {
        flash_erase_sector(i * sector_size);
    }
    
    // 3. 按页写入
    uint32_t offset = 0;
    while (offset < len) {
        uint32_t write_len = (len - offset > page_size) ? page_size : (len - offset);
        flash_write_page(addr + offset, data + offset, write_len);
        offset += write_len;
    }
    
    // 4. 验证
    if (memcmp((void*)addr, data, len) != 0) {
        return -1;  // 写入失败
    }
    
    return 0;  // 成功
}

注意：擦除操作很耗时。一个4KB的扇区，擦除可能需要几十毫秒。如果固件很大（比如1MB），整个擦除过程可能持续好几秒。这时候，看门狗定时器（WDT）可能会超时复位。我曾经因为这个原因，不得不把WDT喂狗逻辑加进擦除循环里。

12.2 跳转到应用程序的准备工作

固件烧好了，接下来就是跳转。但跳转不是简单的goto。你得做好三件事：

  • 关闭中断：跳转前必须关掉所有中断，包括外设中断和系统滴答定时器。
  • 清理外设状态：把用过的外设复位到默认状态。
  • 设置栈指针和PC指针：这是最关键的一步。

为什么会这样？你想想看，如果Bootloader开着中断就跳过去了，应用程序的中断向量表还没初始化，一个中断进来，程序直接跑飞。嗯，我见过这种场景，板子直接死机，只能重新上电。

12.3 栈指针与PC指针设置

这是跳转的核心。ARM Cortex-M系列处理器，启动时从向量表取前两个值：

  • 向量表偏移0x00：栈指针（MSP）初始值
  • 向量表偏移0x04：复位向量（PC指针）初始值

所以，跳转的本质就是：

// 伪代码：跳转到应用程序
typedef void (*app_entry_t)(void);

void jump_to_app(uint32_t app_addr) {
    // 1. 关闭全局中断
    __disable_irq();
    
    // 2. 关闭所有外设中断（具体实现因芯片而异）
    for (int i = 0; i < NUM_IRQS; i++) {
        NVIC_DisableIRQ((IRQn_Type)i);
        NVIC_ClearPendingIRQ((IRQn_Type)i);
    }
    
    // 3. 从应用程序向量表读取栈指针和PC指针
    uint32_t msp = *(volatile uint32_t*)app_addr;
    uint32_t pc  = *(volatile uint32_t*)(app_addr + 4);
    
    // 4. 设置主栈指针
    __set_MSP(msp);
    
    // 5. 跳转到应用程序
    app_entry_t app_entry = (app_entry_t)pc;
    app_entry();
    
    // 这里永远不会返回
}

个人经验：我习惯在跳转前把SysTick定时器也关掉。因为SysTick的中断优先级通常最低，但它的中断向量在应用程序里可能被重新映射了。如果不关，跳转后第一个SysTick中断就会出问题。

12.4 向量表重映射

还有一个容易被忽略的点：向量表重映射。如果应用程序不是从Flash起始地址（0x08000000）运行的，而是从偏移地址（比如0x08020000）运行的，那么应用程序必须重新设置向量表偏移。

在ARM Cortex-M上，通过SCB->VTOR寄存器设置：

// 应用程序启动代码中设置向量表偏移
#define APP_BASE_ADDR 0x08020000

void app_init(void) {
    // 设置向量表偏移
    SCB->VTOR = APP_BASE_ADDR;
    
    // 然后才能使能中断
    __enable_irq();
}

如果不做这一步，中断来了之后，CPU会去Flash起始地址找中断向量，找到的是Bootloader的向量表，而不是应用程序的。结果就是：中断响应完全错乱。

我曾经踩过的坑：有一次做OTA升级，应用程序烧录到0x08040000地址。跳转后，串口中断死活不工作。查了两天，发现是应用程序里忘了设置VTOR。中断来了，CPU跑到Bootloader的向量表里找串口中断处理函数，当然找不到。从那以后，我把VTOR设置写进了应用程序启动代码的第一行。

12.5 完整的跳转流程总结

步骤 操作 说明
1 关闭全局中断 __disable_irq()
2 关闭所有外设中断 逐个关闭并清除挂起标志
3 复位外设到默认状态 防止外设残留状态影响应用程序
4 读取应用程序向量表 获取MSP和PC初始值
5 设置主栈指针 __set_MSP(msp)
6 跳转到应用程序 通过函数指针跳转
7 应用程序设置VTOR 在应用程序启动代码中完成

嗯，到这里，固件烧录和跳转的核心内容就讲完了。说白了，就是两件事：把数据写对，把指针设对。但这两件事，任何一个细节没处理好，板子就起不来。

我个人建议，每次写完跳转代码，先做一次完整的测试：烧录、跳转、运行、中断响应。别偷懒，这个流程值得你花时间验证。

避坑指南：

  • 跳转前一定要关中断，包括SysTick
  • 应用程序一定要设置VTOR（如果地址有偏移）
  • 跳转后不要指望任何Bootloader的全局变量还能用
  • Flash写入过程中要喂狗，防止超时复位
