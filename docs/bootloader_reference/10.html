10、固件下载流程：握手协议设计、数据分包传输、超时重传机制

固件下载，说白了就是给设备“灌程序”。

你想想看，一个刚从产线下来的芯片，里面空空如也，Bootloader 就是那个负责把固件从外面搬进来的“搬运工”。这个搬运过程，可不是简单的复制粘贴。它需要一套严谨的流程，确保数据准确无误地到达目的地。

我个人习惯把固件下载分成三个核心环节：握手、传输、校验。今天我们就重点聊聊前两个，以及那个让人又爱又恨的“超时重传”。

10.1 握手协议设计：先打个招呼

握手，就是设备和上位机（比如你的 PC）互相确认身份的过程。我在项目中遇到过最尴尬的事，就是上位机对着一个还没初始化的设备狂发数据，设备那边一脸懵，根本不搭理。

所以，握手协议要解决两个问题：

  • 你是谁？ 确认设备型号、Bootloader 版本。
  • 准备好了吗？ 确认设备当前状态，是否可以接收数据。

一个典型的握手流程是这样的：

  1. 上位机发送一个特定的握手命令，比如 0xAA 0x55。
  2. 设备收到后，回复自己的设备 ID 和 Bootloader 版本号。
  3. 上位机验证这些信息，如果匹配，就发送“开始下载”指令。
  4. 设备回复“ACK”，表示准备好了。

关键点：握手命令要足够“冷门”，避免和正常数据冲突。我习惯用 0xAA 0x55 0x01 这种三字节序列，降低误触发的概率。

这里有个小坑：有些设备上电后，IO 口状态不确定。我曾经遇到过握手命令被误判为外部中断的情况。嗯，这里要注意，握手前最好先让设备进入一个“监听”状态，比如等待 100ms 再开始握手。

10.2 数据分包传输：大块肉要切着吃

固件文件动辄几百 KB，甚至几 MB。一次传完？不现实。一来缓冲区没那么大，二来万一传错了，重传整个文件代价太高。

所以，我们要把固件切成一个个小包。每个包的大小，取决于你的硬件资源。我常用的包大小是 256 字节或 512 字节。为什么？因为很多 Flash 的页大小就是 256 字节，这样一包数据正好写一页，效率最高。

每个数据包的结构，我建议这样设计：

字段 长度（字节） 说明
包起始符 2 比如 0xAA 0x55，用于同步
包序号 2 从 0 开始，用于排序和重传
数据长度 2 本包有效数据的字节数
数据内容 N 实际的固件数据
校验和 1 或 2 CRC 或简单的累加和

你可能会问：“包序号为什么要 2 字节？” 因为如果固件很大，256 个包可能不够用。2 字节可以支持 65536 个包，每个包 256 字节，算下来能支持 16MB 的固件，足够了。

我的习惯：校验和用 CRC16，虽然计算量比累加和大一点，但检错能力更强。对于 Bootloader 这种“一次失败可能变砖”的场景，这点开销值得。

10.3 超时重传机制：别让设备死等

数据传输过程中，丢包是难免的。可能是线路干扰，可能是上位机卡顿，也可能是设备正在擦除 Flash 没来得及回复。

超时重传机制，就是为了解决这个问题。说白了就是：如果发送方没收到确认，就认为包丢了，重新发一次。

具体怎么设计？我一般分两步：

10.3.1 发送方超时

上位机每发送一个数据包，就启动一个定时器。比如设置 100ms 的超时时间。

  • 如果在 100ms 内收到设备的 ACK，就发送下一个包。
  • 如果超时了还没收到，就重发当前包。
  • 重发次数有限制，比如 3 次。超过 3 次，就报错退出。

10.3.2 接收方超时

设备端也要有超时机制。比如，设备收到一个包后，开始等待下一个包。如果超过 500ms 没收到任何数据，就认为传输中断，自动退出下载模式，回到 Bootloader 主循环。

我曾经踩过的坑：超时时间设得太短。有一次我把发送超时设为 10ms，结果设备在擦除 Flash 时花了 50ms，导致每个包都重传了 3 次，下载速度慢得像蜗牛。后来我把超时时间调整为 200ms，问题就解决了。

记住：超时时间要大于设备处理一个包的最大耗时，包括擦除、写入、校验的时间。

这里有个细节：重传时，包序号不变。设备收到重复的包序号，应该直接丢弃，并回复 ACK。为什么？因为设备可能已经正确接收了，只是 ACK 丢了。如果设备不回复 ACK，上位机就会一直重传，陷入死循环。

10.4 一个简单的代码示例

下面是一个简化的发送端伪代码，展示了超时重传的核心逻辑：

// 发送一个数据包，带超时重传
int send_packet(uint8_t *data, uint16_t len, uint16_t seq) {
    uint8_t retry_count = 0;
    uint8_t ack;

    while (retry_count < MAX_RETRY) {
        // 1. 发送数据包
        uart_send_bytes(data, len);

        // 2. 等待 ACK，超时 100ms
        if (uart_wait_ack(&ack, 100) == SUCCESS) {
            if (ack == ACK_OK) {
                return SUCCESS;  // 发送成功
            }
        }

        // 3. 超时或收到 NAK，重试
        retry_count++;
        printf("重传第 %d 次，包序号 %d\n", retry_count, seq);
    }

    // 4. 重试次数耗尽，返回失败
    return FAILURE;
}

这段代码虽然简单，但已经包含了超时重传的核心思想。实际项目中，你还需要考虑缓冲区管理、流控等问题。

10.5 总结一下

固件下载流程，其实就是一个“可靠传输”的问题。握手协议解决了“谁和谁通信”的问题，分包传输解决了“怎么传”的问题，超时重传解决了“传丢了怎么办”的问题。

我个人觉得，这三个环节里，超时重传是最容易出问题的。时间设短了，效率低；设长了，用户体验差。我的建议是：先根据硬件性能估算一个值，然后在实际测试中微调。
