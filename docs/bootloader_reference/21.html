21、性能优化：启动时间优化、代码尺寸优化、Flash磨损均衡

各位同学，今天我们来聊聊Bootloader的性能优化。说实话，很多人觉得Bootloader只要能跑起来就行，管它快不快、大不大呢。但我在实际项目中吃过不少亏——启动慢半秒，客户投诉；Flash写坏了，产品变砖。嗯，这些坑我都踩过，今天就把经验分享给你们。

21.1 启动时间优化：让设备“秒开”

启动时间，说白了就是从上电到进入主程序的时间。我见过一个项目，Bootloader跑了3秒多，客户直接说“这产品是不是坏了？”你想想看，用户按了开关，等3秒才有反应，体验能好吗？

21.1.1 硬件初始化精简

很多新手喜欢把所有外设都初始化一遍。其实没必要。Bootloader只需要初始化必要的外设：

  • 时钟系统：必须初始化，但别用太慢的时钟源
  • Flash控制器：必须初始化，否则没法读程序
  • 串口/USB：如果不需要升级，就别初始化
  • GPIO：只初始化用到的引脚

我的经验：我曾经在一个项目里，Bootloader初始化了全部12个外设，结果启动花了800ms。后来只保留3个必要的，降到120ms。省下的时间，够用户按两次开关了。

21.1.2 代码执行位置优化

代码在Flash里跑和在RAM里跑，速度差很多。Flash读取有等待周期，RAM没有。所以：

  • 关键代码放RAM：比如Flash擦写函数、中断处理函数
  • 启动阶段代码放RAM：从Flash拷贝到RAM，再跳转执行
// 示例：将关键函数放到RAM中执行
__attribute__((section(".ramfunc")))
void flash_erase_sector(uint32_t addr) {
    // Flash擦除操作
    // 这段代码在RAM中执行，速度更快
}

21.1.3 跳转优化

从Bootloader跳转到应用程序时，很多人会做一次完整的系统复位。其实没必要。我建议：

  • 直接跳转：修改PC指针，跳转到应用程序入口
  • 保留必要状态：比如时钟配置、中断向量表
  • 跳过不必要的初始化：应用程序会重新初始化

注意：直接跳转时，一定要关中断！否则跳转过程中发生中断，程序就飞了。我曾经因为这个bug，调试了整整两天。

21.2 代码尺寸优化：让Bootloader“瘦身”

Bootloader的代码尺寸，直接决定了它占用的Flash空间。你想想看，Flash空间是有限的，Bootloader占多了，应用程序就少了。我见过一个极端案例，Bootloader占了64KB，应用程序只剩64KB，客户想加个功能都加不了。

21.2.1 功能裁剪

Bootloader不需要的功能，一律砍掉：

  • 调试信息：发布版本去掉printf、log输出
  • 错误处理：只保留必要的错误码，不要完整的错误字符串
  • 协议栈：如果只用Ymodem，就别把TCP/IP协议栈加进来

21.2.2 编译器优化

编译器选项能帮你省不少空间：

优化选项 作用 我建议
-Os 尺寸优化 必开，能省30%左右
-ffunction-sections 每个函数独立段 配合--gc-sections使用
--gc-sections 删除未使用的段 必开，能省10-20%
-fno-inline 禁止内联 酌情使用，内联会增大代码

21.2.3 代码复用

Bootloader和应用程序可以共用一些代码：

  • 共用库函数：比如CRC校验、字符串处理
  • 共用驱动：比如串口驱动、Flash驱动
  • 共用头文件：结构体定义、宏定义

避坑指南：我曾经把Bootloader和应用程序的驱动完全分开写，结果Bootloader占了48KB。后来改成共用驱动，降到28KB。省下来的20KB，够放一个不错的功能模块了。

21.3 Flash磨损均衡：让Flash“长寿”

Flash有擦写寿命，一般是1万到10万次。Bootloader经常要擦写Flash，如果不做磨损均衡，某些扇区很快就报废了。我见过一个产品，用了半年就出现Flash坏块，就是因为Bootloader总往同一个扇区写数据。

21.3.1 磨损均衡的原理

说白了，就是把擦写操作分散到不同的扇区。不要总盯着一个扇区写，要轮着来。就像你吃饭，不能总用同一双筷子，得换着用。

21.3.2 实现方法

我常用的方法有两种：

  • 轮询法：按顺序使用扇区，写满一个换下一个
  • 随机法：随机选择一个空闲扇区写入
// 轮询法示例
#define SECTOR_COUNT 8
static uint8_t current_sector = 0;

void write_to_flash(uint8_t *data, uint32_t len) {
    // 写入当前扇区
    flash_write(current_sector * SECTOR_SIZE, data, len);
    
    // 切换到下一个扇区
    current_sector = (current_sector + 1) % SECTOR_COUNT;
    
    // 如果写满了，擦除最旧的扇区
    if (current_sector == 0) {
        flash_erase(SECTOR_COUNT - 1);
    }
}

21.3.3 坏块管理

Flash用久了，难免出现坏块。我建议：

  • 坏块标记：在扇区头部标记是否损坏
  • 坏块跳过：写入时跳过坏块
  • 坏块替换：用备用扇区替换坏块

注意：坏块管理一定要在Bootloader里做。因为应用程序可能没做这个处理，一旦遇到坏块，整个系统就挂了。我有个客户就是吃了这个亏，后来我帮他们加上了坏块管理，再也没出过问题。

21.3.4 实际案例

我之前做的一个物联网项目，设备每天要升级一次固件。如果不做磨损均衡，Flash的寿命只有3年。做了磨损均衡后，寿命延长到10年以上。怎么做的？

  • 分配8个扇区：每个扇区64KB
  • 轮询写入：每次升级写不同的扇区
  • 坏块跳过：遇到坏块自动跳过
  • 备用扇区：预留2个扇区做备用

结果呢？设备运行了5年，Flash还没出过问题。客户说：“这产品真耐用！”

21.4 总结

性能优化这件事，说白了就是“权衡”。启动时间快了，代码可能变大；代码小了，功能可能变少；Flash寿命长了，管理逻辑可能变复杂。我的建议是：

  • 先定目标：启动时间要求多少？代码尺寸限制多少？Flash寿命要求多少？
  • 再选方案：根据目标选择合适的优化方法
  • 最后测试：优化完一定要测试，别让优化引入新bug
