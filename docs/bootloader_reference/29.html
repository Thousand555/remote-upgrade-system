第二十九讲：安全防护——RDP配置、写保护与防回滚

各位同学，今天我们来聊聊Bootloader开发中一个绕不开的话题——安全防护。说实话，早年我做嵌入式的时候，安全这块经常被忽略。直到有一次，一个客户的产品被竞争对手直接读出了固件，复制了个一模一样的东西……嗯，从那以后，我再也不敢轻视安全配置了。

这一讲，我们聚焦三个核心点：读保护（RDP）、写保护，以及防回滚机制。这三板斧用好了，你的固件安全性至少提升一个档次。

一、读保护（RDP）配置

读保护，说白了就是防止别人通过调试接口（比如SWD、JTAG）把你的固件读走。你想想看，如果芯片没有任何保护，随便一根调试器线就能把Flash里的二进制代码dump出来，那你的知识产权就全白给了。

STM32系列里，RDP分为三个级别：

级别 名称 说明
Level 0 无保护 调试接口完全开放，可任意读写Flash
Level 1 读保护 禁止通过调试接口读取Flash，但允许通过用户代码读取
Level 2 永久保护 调试接口永久禁用，不可回退，芯片变“黑盒”

我个人习惯，量产产品至少开到Level 1。Level 2虽然更安全，但一旦开启就再也无法调试了，万一出问题，芯片只能报废。所以除非是极其敏感的产品，否则不建议轻易上Level 2。

配置RDP的代码其实很简单，以STM32为例：

// 设置RDP为Level 1
HAL_FLASH_OB_Unlock();
FLASH_OBProgramInitTypeDef ob_config;
ob_config.OptionType = OPTIONBYTE_RDP;
ob_config.RDPLevel = OB_RDP_LEVEL_1;
HAL_FLASHEx_OBProgram(&ob_config);
HAL_FLASH_OB_Launch();  // 重启生效

注意，这个配置是一次性生效的。写入后需要复位，保护才会真正开启。我在项目中遇到过有人写完代码忘了调用HAL_FLASH_OB_Launch()，结果调试了半天发现Flash还是裸奔的……

警告：RDP Level 1虽然保护了Flash，但RAM中的数据仍然可能被调试器读取。如果你的Bootloader在运行过程中把密钥加载到了RAM里，那这个密钥依然有泄露风险。

二、写保护配置

读保护防的是“读”，写保护防的是“写”。你想想看，如果攻击者不能读你的固件，但可以往你的Flash里写恶意代码，那同样很危险。写保护就是用来锁定某些Flash区域，禁止任何写入操作。

写保护通常按页或按扇区配置。比如STM32F4系列，每个扇区都可以独立设置写保护：

// 保护第2~5扇区不被写入
FLASH_OBProgramInitTypeDef ob_config;
ob_config.OptionType = OPTIONBYTE_WRP;
ob_config.WRPArea = OB_WRPAREA_ZONE_A;
ob_config.WRPStartOffset = 2;
ob_config.WRPEndOffset = 5;
HAL_FLASHEx_OBProgram(&ob_config);
HAL_FLASH_OB_Launch();

这里有个细节要注意：写保护是针对整个扇区的，不能只保护扇区里的某几个字节。所以设计Flash分区时，要把Bootloader、应用程序、配置参数等放在不同的扇区里，这样就能灵活控制。

我曾经见过一个产品，把Bootloader和应用程序放在同一个扇区里，结果想保护Bootloader时，连应用程序也一起锁死了。嗯，这种低级错误其实挺常见的。

小技巧：建议把Bootloader放在最前面的扇区，并开启写保护。这样即使应用程序崩溃了，Bootloader依然完好无损，可以通过OTA或串口重新升级。

三、防回滚机制

防回滚，顾名思义，就是防止固件版本降级。为什么要防回滚？因为旧版本往往存在已知漏洞。攻击者如果能把你的固件刷回有漏洞的版本，那之前打的所有安全补丁就全白费了。

实现防回滚，核心思路就一句话：版本号只增不减。

具体做法是这样的：

  1. 在固件头部预留一个版本号字段（比如4字节）
  2. Bootloader在升级前，读取新固件的版本号
  3. 如果新版本号 ≤ 当前版本号，拒绝升级
  4. 如果新版本号 > 当前版本号，允许升级

代码实现大致如下：

typedef struct {
    uint32_t magic;       // 魔数，用于校验固件合法性
    uint32_t version;     // 版本号，递增
    uint32_t length;      // 固件长度
    uint32_t crc32;       // CRC校验
    uint8_t  data[];      // 固件数据
} firmware_header_t;

bool check_rollback(firmware_header_t *new_fw) {
    uint32_t current_ver = read_current_version();
    if (new_fw->version <= current_ver) {
        // 版本过低，拒绝升级
        return false;
    }
    return true;
}

这里有个坑：版本号存在哪里？如果存在Flash里，那攻击者可以直接修改Flash里的版本号，绕过防回滚检查。我个人建议把版本号存在OTP（一次性可编程）区域或者安全存储区里。OTP写一次就再也改不了了，天然防篡改。

核心要点：防回滚不是单纯比较版本号，而是要确保版本号的存储介质本身是安全的。否则，一切检查都是纸老虎。

四、三者如何配合使用

这三个机制不是孤立的，它们应该协同工作。我一般这样设计：

  • Bootloader区域：开启写保护，防止被篡改。读保护Level 1，防止被读出。
  • 应用程序区域：读保护Level 1，写保护不开启（因为需要OTA升级）。
  • 版本号存储区：放在OTP或安全Flash中，只允许Bootloader写入，应用程序只能读取。

这样设计的好处是：即使应用程序被攻破了，攻击者也改不了Bootloader，也降不了版本。Bootloader就像一道铁闸，牢牢守住最后的安全底线。

好了，这一讲的内容就到这里。安全防护这块，说白了就是“防君子也防小人”。你做得越细致，攻击者的成本就越高。下一讲我们会聊聊安全启动和签名校验，那是更高级的玩法了。
