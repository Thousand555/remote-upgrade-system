14. 看门狗与异常处理：独立看门狗(IWDG)配置、窗口看门狗(WWDG)使用、HardFault异常处理

嵌入式系统跑着跑着就死机了，这事儿你遇到过吧？

我刚开始做产品那会儿，就吃过这个亏。设备在客户现场运行了三天，突然就卡死了，只能断电重启。后来查出来是某个极端条件下，程序陷入了死循环。从那以后，我对看门狗和异常处理就格外上心。

说白了，看门狗就是系统的「保命符」。而异常处理，则是系统最后的「遗言」。今天咱们就把这两样东西彻底搞明白。

14.1 独立看门狗（IWDG）配置

独立看门狗，我习惯叫它「硬狗」。为什么叫「硬」？因为它用的是独立的RC振荡器，主时钟挂了它照样能跑。这在工业环境中特别重要。

14.1.1 IWDG的工作原理

IWDG本质上就是一个递减计数器。你给它设个初值，它就开始往下减。减到0了，系统就复位。你的任务就是在它减到0之前，重新把值填满——这就是所谓的「喂狗」。

关键点：IWDG一旦启动，除了复位，没有任何办法能把它停下来。所以配置一定要谨慎。

14.1.2 配置步骤

配置IWDG其实就三步，我总结一下：

  1. 取消写保护：IWDG的预分频器和重装载寄存器默认是写保护的，需要先解锁
  2. 设置分频系数和重装载值：决定看门狗的溢出时间
  3. 启动IWDG：写入0xCCCC到关键字寄存器

来看个实际代码，这是我项目里用过的配置：

// IWDG配置函数
// 目标溢出时间：约1秒（LSI = 40kHz）
void IWDG_Config(void)
{
    // 1. 取消写保护
    IWDG->KR = 0x5555;
    
    // 2. 设置预分频器为64分频
    // LSI 40kHz / 64 = 625Hz，每个计数周期约1.6ms
    IWDG->PR = IWDG_Prescaler_64;
    
    // 3. 设置重装载值为625
    // 溢出时间 = 625 * 1.6ms ≈ 1秒
    IWDG->RLR = 625;
    
    // 4. 等待寄存器更新完成
    while (IWDG->SR & IWDG_SR_PVU);
    while (IWDG->SR & IWDG_SR_RVU);
    
    // 5. 启动IWDG
    IWDG->KR = 0xCCCC;
    
    // 6. 立即喂狗一次，确保初始状态正常
    IWDG->KR = 0xAAAA;
}

我的经验：喂狗时机很重要。我一般会在主循环的末尾喂狗，而不是在中断里。为什么？如果在中断里喂狗，主循环卡死了，中断还在跑，看门狗就形同虚设了。

14.1.3 溢出时间计算

溢出时间的计算公式很简单：

溢出时间 = (RLR + 1) × 分频系数 / LSI频率

分频系数 PR值 最大溢出时间（LSI=40kHz）
4 0 约0.1秒
8 1 约0.2秒
16 2 约0.4秒
32 3 约0.8秒
64 4 约1.6秒
128 5 约3.2秒
256 6 约6.4秒

注意：LSI频率不是精确的40kHz，它会在30-50kHz之间波动。所以实际溢出时间会有偏差。我一般会留出30%的余量。

14.2 窗口看门狗（WWDG）使用

窗口看门狗，我管它叫「软狗」。它比IWDG多了一个「窗口」的概念。什么意思呢？就是喂狗不能太早，也不能太晚，必须在指定的时间窗口内喂。

14.2.1 为什么需要窗口？

你想想看，如果程序跑飞了，但恰好在一个循环里不断喂狗，那IWDG就失效了。WWDG就是为了解决这个问题——它要求你必须在特定的时间范围内喂狗。太早了说明程序执行太快，可能跳过了某些关键代码；太晚了说明程序卡住了。

14.2.2 WWDG配置示例

// WWDG配置函数
// 使用APB1时钟（36MHz），分频系数8
// 窗口值：0x50，计数器初值：0x7F
void WWDG_Config(void)
{
    // 1. 使能WWDG时钟
    RCC->APB1ENR |= RCC_APB1ENR_WWDGEN;
    
    // 2. 设置分频系数为8
    // 计数时钟 = 36MHz / 4096 / 8 ≈ 1098Hz
    WWDG->CFR = WWDG_CFR_WDGTB_1;  // 分频系数8
    
    // 3. 设置窗口值
    // 必须在计数器值大于0x50时喂狗
    WWDG->CFR |= 0x50;
    
    // 4. 使能唤醒中断（可选）
    WWDG->CFR |= WWDG_CFR_EWI;
    
    // 5. 设置计数器初值并启动
    // 计数器值 = 0x7F，溢出时间约116ms
    WWDG->CR = 0x7F | WWDG_CR_WDGA;
    
    // 6. 配置NVIC优先级
    NVIC_SetPriority(WWDG_IRQn, 3);
    NVIC_EnableIRQ(WWDG_IRQn);
}

// WWDG中断服务函数
void WWDG_IRQHandler(void)
{
    // 清除中断标志
    WWDG->SR = 0;
    
    // 在中断里喂狗
    WWDG->CR = 0x7F;
    
    // 记录喂狗时间，用于调试
    g_last_feed_time = GetSysTick();
}

重要：WWDG的计数器值范围是0x3F到0x7F。低于0x3F时，系统会立即复位。所以喂狗时，必须把计数器值设置到0x40以上。

14.2.3 IWDG vs WWDG 选型建议

特性 IWDG WWDG
时钟源 独立RC振荡器 系统时钟（APB1）
精度 较低（30%-50%偏差） 高（与系统时钟一致）
窗口功能 无 有
停止模式 继续运行 停止
典型应用 系统级保护 任务时序监控

我个人习惯是：关键系统用IWDG做最后防线，任务调度用WWDG做时序监控。两者配合使用，效果最好。

14.3 HardFault异常处理

HardFault，说白了就是系统出了它自己都搞不定的错误。比如访问了不存在的地址、执行了非法指令、除数为零等等。这时候系统会跳转到HardFault处理函数。

14.3.1 常见的HardFault原因

  • 指针越界：野指针、数组越界访问
  • 栈溢出：递归太深、局部变量太大
  • 中断优先级配置错误：导致中断嵌套异常
  • 外设访问时序错误：比如在时钟没准备好时访问外设

我曾经遇到过一个坑：在中断里调用了printf函数，而printf内部用了动态内存分配。结果堆栈冲突，直接HardFault。从那以后，我定了个规矩——中断里绝不调用标准库函数。

14.3.2 捕获HardFault现场信息

系统进入HardFault时，会保存一些关键寄存器。把这些信息记录下来，对定位问题非常有帮助。

// HardFault处理函数
void HardFault_Handler(void)
{
    // 获取堆栈指针
    uint32_t *stack_ptr;
    
    // 判断是MSP还是PSP
    if (__get_IPSR() & 0xFF)  // 在中断中
    {
        stack_ptr = (uint32_t*)__get_MSP();
    }
    else
    {
        stack_ptr = (uint32_t*)__get_PSP();
    }
    
    // 保存关键寄存器信息
    FaultInfo.R0 = stack_ptr[0];
    FaultInfo.R1 = stack_ptr[1];
    FaultInfo.R2 = stack_ptr[2];
    FaultInfo.R3 = stack_ptr[3];
    FaultInfo.R12 = stack_ptr[4];
    FaultInfo.LR = stack_ptr[5];
    FaultInfo.PC = stack_ptr[6];
    FaultInfo.xPSR = stack_ptr[7];
    
    // 保存到非易失存储器（如Flash或EEPROM）
    SaveFaultInfoToFlash(&FaultInfo);
    
    // 记录错误日志
    LogError("HardFault occurred at PC: 0x%08X", FaultInfo.PC);
    
    // 系统复位
    NVIC_SystemReset();
    
    while(1);
}

14.3.3 实用的调试技巧

光捕获信息还不够，还得会分析。我分享几个实用技巧：

  1. 查看PC指针：PC指向的地址就是出错的指令位置。用反汇编工具查看这个地址附近的代码。
  2. 分析LR寄存器：LR里存的是返回地址，能告诉你是在哪个函数里出的问题。
  3. 检查栈回溯：通过栈里的返回地址，可以还原出函数调用链。

我的调试流程：拿到PC地址 → 反汇编查看指令 → 分析是哪种异常（总线错误、用法错误等）→ 检查相关变量和外设状态 → 定位问题根源。

14.3.4 预防措施

与其等HardFault发生了再处理，不如提前预防。我总结了几个经验：

  • 启用MPU：内存保护单元可以防止非法访问，在MPU触发异常时，信息比HardFault更详细
  • 使用断言：在关键参数传入时做合法性检查
  • 栈空间监控：定期检查栈使用情况，防止溢出
  • 外设访问加锁：对共享资源使用互斥访问

切记：HardFault处理函数里不要做复杂操作。我见过有人在里面调用printf、malloc，结果再次触发HardFault，形成死循环。简单记录、保存现场、复位，就够了。

好了，看门狗和异常处理就讲到这里。这些东西平时可能用不上，但一旦出了问题，就是救命稻草。我建议你在项目初期就把这些机制加上，别等到出问题了再补——那时候往往已经晚了。
