18、多分区管理：分区表设计、分区属性定义、动态分区管理

各位同学，今天我们来聊聊Bootloader里一个非常核心的话题——多分区管理。

说实话，我刚开始做嵌入式开发那会儿，对分区的理解特别肤浅。就觉得嘛，Flash这么大，划几块区域存代码、存数据不就完了？直到有一次，我在一个OTA项目里栽了大跟头——升级到一半断电了，整个设备变砖。嗯，从那以后我才真正开始认真研究分区管理。

18.1 为什么需要多分区？

你想想看，一个嵌入式设备，Flash里要放的东西可不少：

  • Bootloader本身
  • 应用程序（可能还有备份）
  • 配置参数
  • 日志信息
  • 文件系统

如果所有东西都挤在一起，升级、回滚、数据保护都无从谈起。说白了，分区就是给Flash做「功能分区」，各司其职。

核心原则：分区设计的目标是——隔离、保护、可管理。

18.2 分区表设计

分区表，就是一张「地图」。它告诉Bootloader：每个分区从哪里开始、到哪里结束、干什么用的。

我个人习惯把分区表放在Flash的固定位置，比如偏移0x0000处。这样Bootloader启动时，第一件事就是读分区表，然后才知道该去哪找应用程序。

18.2.1 分区表的基本结构

一个典型的分区表条目，至少包含这些字段：

字段 大小 说明
分区名称 16字节 字符串，如"bootloader"、"app"、"config"
起始地址 4字节 Flash中的偏移地址
分区大小 4字节 字节数
分区属性 4字节 位掩码，定义读写、可执行等属性
校验和 4字节 用于验证分区表完整性

我在项目中遇到过一个问题：分区表本身被破坏了怎么办？所以我会在Flash末尾再存一份备份分区表。启动时先读主表，校验失败就自动切到备份表。这招救过我不少次。

18.2.2 分区表在代码中的定义

// 分区表条目结构体
typedef struct {
    char     name[16];        // 分区名称
    uint32_t start_addr;      // 起始地址
    uint32_t size;            // 分区大小
    uint32_t attributes;      // 分区属性
    uint32_t checksum;        // 校验和
} partition_entry_t;

// 分区表整体结构
typedef struct {
    uint32_t magic;           // 魔数，用于识别
    uint32_t version;         // 分区表版本
    uint32_t entry_count;     // 分区条目数量
    partition_entry_t entries[MAX_PARTITIONS];
    uint32_t table_checksum;  // 整个表的校验和
} partition_table_t;

小技巧：魔数（magic）我一般用0x50415254（即"PART"的ASCII码）。这样在调试时，用内存查看工具一眼就能认出分区表。

18.3 分区属性定义

分区属性，说白了就是给每个分区打标签。比如：这个分区能不能写？能不能执行？是不是关键数据？

我习惯用位掩码来定义属性：

// 分区属性定义
#define PART_ATTR_READABLE      (1 << 0)  // 可读
#define PART_ATTR_WRITABLE      (1 << 1)  // 可写
#define PART_ATTR_EXECUTABLE    (1 << 2)  // 可执行（代码分区）
#define PART_ATTR_BOOTABLE      (1 << 3)  // 可引导（Bootloader从这里启动）
#define PART_ATTR_CRITICAL      (1 << 4)  // 关键分区（不可删除）
#define PART_ATTR_ACTIVE        (1 << 5)  // 当前激活分区（用于A/B升级）
#define PART_ATTR_UPDATE_PENDING (1 << 6) // 待更新分区

举个例子，一个典型的应用程序分区，属性可能是：PART_ATTR_READABLE | PART_ATTR_EXECUTABLE | PART_ATTR_BOOTABLE。而配置参数分区，则是PART_ATTR_READABLE | PART_ATTR_WRITABLE，但不能执行。

注意：千万不要把可执行属性赋给数据分区！我曾经见过一个产品，因为配置分区被错误标记为可执行，结果一个缓冲区溢出攻击直接让攻击者执行了任意代码。嗯，那场面相当尴尬。

18.4 动态分区管理

静态分区表虽然简单，但不够灵活。比如，你需要在运行时创建一个临时分区来存放下载的固件包，或者调整分区大小。这时候就需要动态分区管理了。

18.4.1 动态分区的核心思想

说白了，动态分区就是「按需分配」。Bootloader在启动时，根据当前Flash的剩余空间，动态创建、删除、调整分区。

我建议的做法是：

  1. 保留一个「空闲分区」作为动态分配的资源池
  2. 需要时，从空闲分区中切出一块，创建新分区
  3. 不需要时，将分区释放回空闲池

18.4.2 动态分区管理接口

// 创建分区
int partition_create(const char* name, uint32_t size, uint32_t attributes);

// 删除分区
int partition_delete(const char* name);

// 调整分区大小
int partition_resize(const char* name, uint32_t new_size);

// 查找分区
partition_entry_t* partition_find(const char* name);

// 列出所有分区
void partition_list(void);

我在实现动态分区时，遇到过一个大坑：碎片化。频繁创建和删除分区，会导致Flash上出现很多小碎片，最终无法分配大块连续空间。我的解决方案是——在删除分区时，主动触发一次「碎片整理」，把空闲区域合并成一个大块。

避坑指南：我曾经在动态分区里忘记处理「分区重叠」的问题。两个分区不小心指向了同一块Flash区域，结果写一个分区把另一个分区的数据给覆盖了。所以，每次创建或调整分区时，一定要做重叠检测。

18.4.3 动态分区的实际应用场景

举个例子，OTA升级时：

  • Bootloader从服务器下载新固件，先创建一个临时分区存放
  • 下载完成后，校验固件完整性
  • 校验通过，将临时分区标记为「待激活」
  • 下次重启时，Bootloader将临时分区的内容复制到主应用分区
  • 最后删除临时分区，释放空间

整个过程，分区表一直在动态变化。嗯，这就是动态分区管理的魅力所在。

18.5 分区表的安全与校验

分区表一旦被篡改，整个系统就乱了。所以，我强烈建议：

  • 分区表使用CRC32或SHA256做完整性校验
  • 关键分区（如Bootloader自身）设置为只读
  • 分区表本身存储在受保护的Flash区域（如OTP或安全区）
// 计算分区表校验和
uint32_t partition_table_calc_checksum(partition_table_t* table) {
    uint32_t checksum = 0;
    uint8_t* data = (uint8_t*)table;
    // 跳过校验和字段本身
    uint32_t len = sizeof(partition_table_t) - sizeof(uint32_t);
    for (uint32_t i = 0; i < len; i++) {
        checksum += data[i];
    }
    return checksum;
}

// 验证分区表
bool partition_table_verify(partition_table_t* table) {
    if (table->magic != PARTITION_TABLE_MAGIC) {
        return false;
    }
    uint32_t calc = partition_table_calc_checksum(table);
    return (calc == table->table_checksum);
}

个人经验：我习惯在分区表里加一个「版本号」字段。这样，当固件升级后分区表结构发生变化时，Bootloader可以自动迁移旧分区表到新格式。这个设计让我少改了很多兼容性Bug。

18.6 小结

多分区管理，说白了就是给Flash做「精细化管理」。分区表是地图，分区属性是规则，动态分区是灵活手段。这三者配合好了，你的Bootloader才能稳定、安全、可升级。

最后送大家一句话：分区设计时多花一小时，调试时少花一整天。别问我怎么知道的，都是泪。
