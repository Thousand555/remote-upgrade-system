第8章 串口通信协议：UART基础与配置、自定义通信协议设计、数据校验与错误处理

串口通信，在嵌入式世界里可以说是最基础、也最常用的通信方式了。我做了这么多年Bootloader开发，几乎每个项目都离不开它。说白了，UART就是两根线——TX和RX，一收一发，简单粗暴。但越是简单的东西，越容易在细节上翻车。今天我就把UART的那些门道，还有怎么设计一套靠谱的自定义协议，一次性讲清楚。

8.1 UART基础与配置

UART的全称是Universal Asynchronous Receiver/Transmitter，通用异步收发器。为什么叫异步？因为它没有单独的时钟线。收发双方靠的是约定好的波特率来同步。你想想看，没有时钟线，两边各干各的，全靠速率匹配，这其实挺考验精度的。

我在项目中遇到过最典型的问题，就是波特率偏差。比如你设了115200，但晶振精度不够，或者分频系数算错了，实际跑出来可能是115400。短时间通信没问题，但连续发几百个字节后，误差累积，就开始丢字节了。嗯，这里要注意，波特率误差最好控制在±2%以内，超过这个范围，通信可靠性会急剧下降。

UART帧格式（8N1为例）

起始位(1bit) + 数据位(8bit) + 校验位(无) + 停止位(1bit) = 10bits

传输1字节实际需要10个bit时间，所以实际吞吐量 = 波特率 / 10

配置UART时，我建议你重点关注这几个参数：

  • 波特率：常用9600、19200、38400、115200。Bootloader里我一般用115200，调试阶段够快，稳定性也还行。
  • 数据位：通常是8位。7位的情况很少见了，除非你还在跟老古董设备通信。
  • 校验位：None、Even、Odd。我个人习惯用None，因为校验位只能检错不能纠错，意义不大。后面我会讲更靠谱的校验方式。
  • 停止位：1位或2位。2位主要是给老设备用的，现代MCU用1位就够了。

下面是一个典型的UART初始化代码，以STM32为例：

void UART_Init(uint32_t baudrate)
{
    // 使能USART1时钟
    RCC->APB2ENR |= RCC_APB2ENR_USART1EN;
    RCC->AHB1ENR |= RCC_AHB1ENR_GPIOAEN;

    // 配置TX(PA9)为复用推挽输出，RX(PA10)为浮空输入
    GPIOA->MODER |= GPIO_MODER_MODER9_1;  // 复用功能
    GPIOA->AFR[1] |= 7 << 4;              // AF7 = USART1
    GPIOA->MODER &= ~GPIO_MODER_MODER10_0; // 输入模式

    // 计算波特率：USARTDIV = PCLK2 / (16 * baudrate)
    uint32_t usartdiv = 84000000 / (16 * baudrate);
    USART1->BRR = usartdiv;

    // 使能发送、接收、USART
    USART1->CR1 = USART_CR1_TE | USART_CR1_RE | USART_CR1_UE;
}

小技巧：调试阶段，我习惯在UART初始化后发一个0x55（二进制01010101），用示波器看波形。如果波形规整，说明波特率配置没问题。这招帮我省了不少排查时间。

8.2 自定义通信协议设计

裸的UART只能传字节，但实际项目中我们需要传的是"有意义的数据"。比如我要给Bootloader发一条"擦除第3扇区"的命令，总不能直接发个0x03吧？万一误触发了呢？所以，我们需要一套自定义协议。

我设计协议的原则很简单：帧头 + 数据 + 校验。帧头用来同步，数据用来承载信息，校验用来保证正确性。下面是我在Bootloader项目中常用的一种协议格式：

字段 长度 说明
帧头 2字节 固定值 0xAA 0x55，用于帧同步
长度 1字节 数据域的长度（不含帧头和校验）
命令 1字节 0x01=擦除, 0x02=写入, 0x03=读取...
数据 N字节 实际载荷，长度由"长度"字段决定
校验 1字节 从"长度"到"数据"末尾的累加和

为什么帧头要用两个字节？因为单字节0xAA有可能出现在数据里，用双字节可以大大降低误同步的概率。我曾经见过有人只用单字节帧头，结果数据里连续出现0xAA，接收端直接乱套了。

协议解析的代码实现，我一般用状态机：

typedef enum {
    STATE_IDLE,
    STATE_HEADER1,
    STATE_HEADER2,
    STATE_LENGTH,
    STATE_CMD,
    STATE_DATA,
    STATE_CHECKSUM
} ProtocolState;

uint8_t Protocol_Parse(uint8_t byte)
{
    static ProtocolState state = STATE_IDLE;
    static uint8_t rx_buffer[256];
    static uint8_t rx_index = 0;
    static uint8_t data_len = 0;
    static uint8_t checksum = 0;

    switch(state) {
        case STATE_IDLE:
            if(byte == 0xAA) state = STATE_HEADER1;
            break;
        case STATE_HEADER1:
            if(byte == 0x55) state = STATE_LENGTH;
            else state = STATE_IDLE;  // 同步失败，重新开始
            break;
        case STATE_LENGTH:
            data_len = byte;
            rx_index = 0;
            checksum = byte;  // 开始累加校验
            state = STATE_CMD;
            break;
        case STATE_CMD:
            rx_buffer[rx_index++] = byte;
            checksum += byte;
            state = STATE_DATA;
            break;
        case STATE_DATA:
            rx_buffer[rx_index++] = byte;
            checksum += byte;
            if(rx_index >= data_len) state = STATE_CHECKSUM;
            break;
        case STATE_CHECKSUM:
            if(checksum == byte) {
                // 校验通过，处理命令
                ProcessCommand(rx_buffer[0], &rx_buffer[1], data_len - 1);
            }
            state = STATE_IDLE;
            break;
    }
    return 0;
}

注意：状态机里一定要加超时处理。如果收到帧头后，后续字节迟迟不来，要能自动复位到空闲状态。否则一个错误字节就能让你的协议解析器"卡死"。

8.3 数据校验与错误处理

串口通信在工业现场很容易受干扰。电机启停、继电器吸合，都会在线上感应出噪声。所以，光靠协议格式还不够，必须要有校验机制。

常用的校验方式有这么几种：

  • 累加和校验：把所有数据字节加起来，取低8位。简单，但检错能力一般。两个bit翻转可能互相抵消。
  • CRC校验：循环冗余校验。检错能力很强，但计算量稍大。Bootloader里我常用CRC16。
  • 异或校验：把所有字节异或一遍。比累加和好一点，但也不够强。

我个人习惯在Bootloader中用CRC16。为什么？因为固件传输动辄几十KB，一个bit错误都可能导致刷机变砖。累加和在这种场景下不够可靠。我曾经在一个项目中用累加和做校验，结果连续传了三次都校验通过，但刷进去的固件就是跑不起来。后来一查，是某段数据里同时错了两个bit，累加和恰好没变。从那以后，涉及固件传输的场景，我坚决用CRC。

CRC16的查表法实现，效率很高：

uint16_t CRC16_Calc(uint8_t *data, uint16_t len)
{
    uint16_t crc = 0xFFFF;
    uint16_t i;
    uint8_t index;

    while(len--) {
        index = (crc ^ *data++) & 0xFF;
        crc = (crc >> 8) ^ crc16_table[index];
    }
    return crc ^ 0xFFFF;
}

// CRC16查表（多项式0x8005，标准Modbus）
static const uint16_t crc16_table[256] = {
    0x0000, 0xC0C1, 0xC181, 0x0140, 0xC301, 0x03C0, 0x0280, 0xC241,
    // ... 此处省略完整表格，实际使用时需要256个值
};

错误处理方面，我建议你至少做这三件事：

  1. 帧超时检测：两个字节之间超过一定时间（比如10ms），认为帧结束，丢弃不完整的数据。
  2. 重传机制：接收方校验失败后，发送NAK，发送方收到NAK后重传上一帧。重传次数建议限制在3次以内，超过就报错。
  3. 日志记录：把错误类型和发生时间记录下来。调试阶段特别有用，能帮你定位是硬件干扰还是软件bug。

避坑指南：我曾经在Bootloader里只做了校验，没做重传。结果有一次在车间刷机，电磁干扰特别大，连续丢帧。操作员反复拔插电源重启，最后把Flash刷坏了。后来我加上了重传机制，再也没出过类似问题。记住，校验只能发现问题，重传才能解决问题。

好了，关于UART通信协议，核心内容就这些。从硬件配置到协议设计，再到校验和错误处理，每一步都有坑，但也都有对应的解法。你把这些吃透了，Bootloader的通信层基本就稳了。下一章我们聊聊Flash驱动，那又是另一片天地。
