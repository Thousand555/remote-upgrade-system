6、中断向量表重映射：向量表的工作原理、重映射的必要性、在Bootloader中实现向量表重定位

好，咱们今天聊一个在Bootloader开发里绕不开的话题——中断向量表重映射。说实话，这玩意儿刚接触的时候我也觉得挺玄乎的，不就是个跳转表吗？但后来在实际项目中踩过坑之后，才真正明白它有多重要。

6.1 向量表的工作原理

先说说向量表到底是什么。说白了，它就是一张“地址表”。这张表里存的是各种中断服务函数（ISR）的入口地址。CPU一旦检测到某个中断发生，就会根据中断号去这张表里查，找到对应的函数地址，然后跳过去执行。

以ARM Cortex-M系列为例，向量表通常放在Flash的起始地址，也就是0x00000000处。表的前几个条目是固定的：

; 典型的Cortex-M向量表布局
0x00000000: 栈顶指针 (MSP初始值)
0x00000004: 复位向量 (Reset_Handler)
0x00000008: NMI中断向量
0x0000000C: 硬错误中断向量
...
0x00000040: SysTick中断向量
...

嗯，这里要注意一点：向量表里存的不是函数本身，而是函数的地址。CPU拿到这个地址后，再跳转到对应的代码段去执行。我刚开始做的时候，总以为向量表里直接放的是指令，结果调试了半天发现中断进不去——其实就是这个理解偏差导致的。

6.2 重映射的必要性

为什么要重映射？你想想看，Bootloader和应用程序通常放在Flash的不同区域。比如Bootloader在0x08000000~0x08003FFF，应用程序在0x08004000之后。但CPU一上电，默认的向量表还是在0x08000000（也就是Flash起始地址）。

这时候问题就来了：如果应用程序里使能了某个中断，比如定时器中断，CPU会去查向量表。但它查的是0x08000000处的表，而不是应用程序自己的向量表。结果就是——它找到了Bootloader里对应的中断处理函数，而不是应用程序的。这能不出问题吗？

核心问题：中断发生后，CPU只会去固定的地址查向量表。如果不重映射，应用程序的中断永远无法被正确响应。

我在项目中遇到过这样一个情况：有个同事把Bootloader和应用程序的向量表都放在Flash起始位置，结果应用程序里的按键中断死活不触发。查了两天，最后发现是向量表没重映射，CPU一直在执行Bootloader里的空中断函数。你说冤不冤？

所以，重映射的必要性可以总结为三点：

  • 地址隔离：Bootloader和应用程序各有各的向量表，必须分开存放
  • 中断正确响应：应用程序使能的中断，必须由应用程序自己的ISR来处理
  • 系统稳定性：避免误入Bootloader的中断处理函数，导致系统行为异常

6.3 在Bootloader中实现向量表重定位

好，接下来咱们看看具体怎么实现。不同架构的MCU，实现方式略有不同。我以最常用的ARM Cortex-M系列为例，讲两种主流方法。

6.3.1 方法一：修改VTOR寄存器

Cortex-M内核提供了一个叫VTOR（Vector Table Offset Register）的寄存器。这个寄存器的作用就是告诉CPU：向量表不在默认位置了，挪到别处去了。你只要往这个寄存器里写入新的基地址，CPU就会去新地址查表。

代码实现非常简单：

// 假设应用程序的向量表放在0x08004000处
#define APP_VECTOR_TABLE_ADDR 0x08004000

void jump_to_application(void)
{
    // 1. 关闭全局中断
    __disable_irq();
    
    // 2. 重映射向量表到应用程序区域
    SCB->VTOR = APP_VECTOR_TABLE_ADDR;
    
    // 3. 读取应用程序的栈顶指针和复位向量
    uint32_t app_stack_top = *(uint32_t*)APP_VECTOR_TABLE_ADDR;
    uint32_t app_reset_vector = *(uint32_t*)(APP_VECTOR_TABLE_ADDR + 4);
    
    // 4. 设置主栈指针
    __set_MSP(app_stack_top);
    
    // 5. 跳转到应用程序的复位向量
    void (*app_main)(void) = (void (*)(void))app_reset_vector;
    app_main();
    
    // 注意：这里不会返回
}

个人经验：我建议在跳转之前，先把Bootloader用到的所有外设都复位一遍。否则应用程序启动时，某些外设还处于Bootloader配置的状态，容易出问题。我曾经因为这个原因，应用程序的串口怎么都初始化不对，后来发现是Bootloader没关DMA。

6.3.2 方法二：使用分散加载文件

有些场景下，你可能不想在代码里显式修改VTOR，而是希望链接器直接把向量表放到指定位置。这时候可以用分散加载文件（或者叫链接脚本）来实现。

以GCC链接脚本为例：

/* 应用程序的链接脚本片段 */
MEMORY
{
    FLASH (rx) : ORIGIN = 0x08004000, LENGTH = 64K
    RAM (rw)   : ORIGIN = 0x20000000, LENGTH = 20K
}

SECTIONS
{
    .isr_vector :
    {
        . = ALIGN(4);
        KEEP(*(.isr_vector))  /* 向量表段 */
        . = ALIGN(4);
    } > FLASH
    
    /* 其他段... */
}

这样编译出来的应用程序，向量表自然就在0x08004000了。然后在Bootloader里，只需要在跳转前设置VTOR即可。

注意：向量表必须按4字节对齐，而且地址的低7位必须为0（Cortex-M要求）。我曾经犯过一个低级错误，把向量表地址写成了0x08004001，结果中断全乱了。调试了半天才发现是对齐问题。

6.3.3 方法三：运行时复制向量表到RAM

还有一种场景：应用程序需要动态修改中断处理函数。比如你想在运行时注册一个自定义的中断服务函数。这时候，向量表就不能放在Flash里了（Flash是只读的），得搬到RAM里。

实现思路：

  1. 在RAM中开辟一块空间，大小和向量表一致
  2. 把Flash里的向量表内容复制到RAM中
  3. 修改VTOR，指向RAM中的向量表
  4. 之后就可以动态修改RAM中的向量表条目了
#define VECTOR_TABLE_SIZE 256  // 假设有256个中断向量

// RAM中的向量表缓冲区
uint32_t ram_vector_table[VECTOR_TABLE_SIZE] __attribute__((aligned(512)));

void relocate_vector_table_to_ram(void)
{
    // 1. 从Flash复制向量表到RAM
    uint32_t *flash_table = (uint32_t*)SCB->VTOR;
    for(int i = 0; i < VECTOR_TABLE_SIZE; i++)
    {
        ram_vector_table[i] = flash_table[i];
    }
    
    // 2. 重映射到RAM
    SCB->VTOR = (uint32_t)ram_vector_table;
    
    // 3. 使能RAM区域的写权限（如果需要）
    // 某些MCU需要配置MPU或内存保护单元
}

避坑指南：我曾经在STM32F4上做过这个方案，结果发现复制完向量表后，系统立即进入HardFault。后来查手册才知道，Cortex-M4的向量表要求地址的低9位为0（因为表大小是512字节对齐的）。所以分配RAM缓冲区时，一定要用__attribute__((aligned(512)))强制对齐。

6.4 总结一下

向量表重映射这件事，说白了就是让CPU知道：你的中断处理函数搬家了，别去老地方找了。实现方式无非三种：

  • 修改VTOR：最简单直接，适合大多数场景
  • 链接脚本控制：适合对代码布局有严格要求的项目
  • 复制到RAM：适合需要动态修改中断处理函数的场景

我个人习惯用第一种方法，代码量少，逻辑清晰。但如果你做的是RTOS或者需要热补丁的系统，那第三种方法会更灵活。嗯，具体选哪种，看你的项目需求吧。

最后提醒一句：不管用哪种方法，跳转到应用程序之前，一定要把Bootloader用到的中断全部关掉。否则应用程序启动过程中，突然来了个Bootloader的定时器中断，那画面太美我不敢看。
