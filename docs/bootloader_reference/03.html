第三章 开发环境搭建：Keil MDK安装与配置、GCC工具链搭建、调试器（J-Link/ST-Link）使用

好，咱们进入第三章。说实话，Bootloader开发这件事，七分靠思路，三分靠工具。环境没搭好，后面全是坑。我见过太多新手，代码写得挺漂亮，结果一烧录就黑屏，最后发现是编译器版本不对。所以这一章，咱们把吃饭的家伙先收拾利索。

3.1 Keil MDK：老牌IDE的安装与配置

Keil MDK，圈内俗称“Keil”，是ARM Cortex-M系列开发的事实标准。我个人习惯用它做原型验证，因为上手快，调试信息直观。

3.1.1 安装步骤

  1. 下载安装包：去ARM官网或Keil官网，找MDK-Arm最新版。注意区分32位和64位。
  2. 运行安装程序：一路Next，但安装路径不要有中文。我曾经帮一个同事排查问题，折腾了两小时，最后发现他装在了“D:\开发工具\Keil_v5”……嗯，中文路径在编译链接时偶尔会抽风。
  3. 激活License：安装完后打开uVision，点击File → License Management。如果你有正版License，直接粘贴；如果是评估版，注意代码大小限制（通常32KB）。做Bootloader的话，32KB其实够用，但别超了。
  4. 安装器件包（Pack）：点击Pack Installer，找到你的芯片型号。比如STM32F103，勾选并安装。这一步很多人忘，结果编译时报“device not found”。
注意：Keil MDK版本和器件包版本要匹配。MDK 5.36以上对某些老芯片支持有问题。我建议：做新项目用最新版，维护老项目用稳定版（比如5.33）。

3.1.2 工程配置要点

新建工程时，有几个关键地方要设对：

  • Target选项卡：ARM Compiler选“Use default compiler version 6”或“V5”。V6编译快，但V5兼容性好。做Bootloader我推荐V5，因为有些底层汇编指令V6不支持。
  • Output选项卡：勾选“Create HEX File”。Bootloader最终烧录的是HEX或BIN文件，不勾选你烧什么？
  • C/C++选项卡：Optimization选“Level 0 (-O0)”。调试阶段别开优化，否则单步执行时变量值可能“凭空消失”。
小技巧：在“C/C++”选项卡的“Define”里加上“USE_STDPERIPH_DRIVER”。这是标准外设库的宏定义，不加的话，很多外设函数会报未定义。

3.2 GCC工具链：开源世界的自由与力量

Keil虽好，但它是收费的。如果你做开源项目，或者想跨平台开发（比如在Linux下写Bootloader），GCC工具链是首选。说白了，GCC就是编译器界的Linux——免费、强大、但需要自己折腾。

3.2.1 搭建ARM GCC工具链

我推荐用ARM官方的“GNU Arm Embedded Toolchain”。下载后解压到某个目录，比如C:\gcc-arm-none-eabi。然后配置环境变量：

# Windows下
set PATH=%PATH%;C:\gcc-arm-none-eabi\bin

# Linux下
export PATH=$PATH:/opt/gcc-arm-none-eabi/bin

验证是否成功：打开终端，输入arm-none-eabi-gcc --version。如果看到版本号，说明成了。

避坑指南：我曾经在Windows下用GCC编译一个Bootloader，结果链接时报“undefined reference to __main”。查了半天，发现是启动文件里调用了C库初始化函数，但GCC的链接脚本没包含对应的库。解决方案：在链接脚本里加上--specs=nano.specs和--specs=nosys.specs。

3.2.2 Makefile编写示例

用GCC开发，通常配合Makefile。下面是一个最小化的Makefile模板：

# 工具链前缀
PREFIX = arm-none-eabi-
CC = $(PREFIX)gcc
LD = $(PREFIX)ld
OBJCOPY = $(PREFIX)objcopy

# 编译选项
CFLAGS = -mcpu=cortex-m3 -mthumb -O0 -g -Wall
LDFLAGS = -T linker.ld -nostartfiles

# 源文件
SRCS = main.c startup.c
OBJS = $(SRCS:.c=.o)

# 目标
all: bootloader.elf bootloader.bin

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

bootloader.elf: $(OBJS)
	$(LD) $(LDFLAGS) $^ -o $@

bootloader.bin: bootloader.elf
	$(OBJCOPY) -O binary $< $@

clean:
	rm -f *.o *.elf *.bin

你想想看，这个Makefile其实就干了三件事：编译、链接、生成二进制。但很多新手会卡在链接脚本（linker.ld）上。嗯，链接脚本决定了代码段、数据段放在哪里，对Bootloader来说至关重要。我们后面会专门讲。

3.3 调试器：J-Link与ST-Link的使用

调试器是开发者的眼睛。没有它，你只能靠printf猜问题。我个人更偏爱J-Link，因为它速度快、功能全。但ST-Link免费，配合STM32CubeIDE用也很香。

3.3.1 J-Link：专业调试利器

J-Link是SEGGER公司的产品。安装驱动后，连接开发板，打开J-Link Commander：

J-Link> connect
Device> STM32F103C8
Target interface> SWD
Speed> 4000
Connecting to target... OK

连接成功后，你可以用loadbin命令烧录二进制文件：

J-Link> loadbin bootloader.bin 0x08000000
注意：J-Link的SWD速度别设太高。我遇到过在4000kHz下调试正常，但一上电就跑飞的情况。后来降到1000kHz就稳了。原因可能是线太长或干扰。

3.3.2 ST-Link：STM32的官方搭档

ST-Link集成在Nucleo和Discovery板上，也可以单独买。使用ST-Link需要安装STM32CubeProgrammer或OpenOCD。我个人习惯用OpenOCD，因为它开源且支持脚本化：

# 烧录命令
openocd -f interface/stlink.cfg -f target/stm32f1x.cfg -c "program bootloader.bin 0x08000000 verify reset exit"

这里verify参数会校验烧录是否正确。我曾经有一次烧录后芯片不工作，就是靠verify发现某个地址写错了——原来是链接脚本里Flash起始地址设成了0x08001000，但实际应该从0x08000000开始。

3.3.3 调试器对比

特性 J-Link ST-Link
速度 最高50MHz 最高4MHz
断点数量 无限（硬件+软件） 6个硬件断点
价格 几百到几千元 几十元（或免费随板）
适用场景 复杂调试、性能分析 日常开发、学习

怎么选？如果你只是学Bootloader，ST-Link完全够用。但如果你要做RTOS调试、Trace分析，J-Link的RTT和Event Recorder功能会让你爱不释手。

3.4 环境验证：烧录一个点灯程序

环境搭没搭好，跑个点灯程序就知道了。我建议你写一个最简单的Bootloader雏形——其实就是让LED闪烁，但通过调试器单步执行，观察寄存器变化。具体步骤：

  1. 用Keil或GCC编译一个点灯程序，生成HEX文件。
  2. 用J-Link或ST-Link烧录到Flash的0x08000000地址。
  3. 复位开发板，看LED是否闪烁。
  4. 如果没亮，检查接线、调试器驱动、烧录地址。
我的经验：第一次烧录时，别急着写复杂逻辑。先确认“最小系统”能跑起来——时钟配置、GPIO初始化、延时函数。这三个对了，Bootloader的骨架就有了。

好了，环境搭建就到这里。下一章咱们正式进入Bootloader的核心——启动流程分析。到时候你会明白，为什么环境搭建这么重要——因为调试Bootloader时，每一步都可能踩坑，而好的工具能帮你快速定位问题。
