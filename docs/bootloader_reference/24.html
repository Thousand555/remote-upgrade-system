第24章：单元测试与模拟：Cmock/Ceedling框架使用、Flash驱动模拟测试、通信协议测试

说实话，很多做Bootloader的同行，一听到「单元测试」就觉得是上层应用的事。我当年也这么想——嵌入式嘛，硬件耦合那么紧，测什么测？直到有一次，一个Flash驱动的小bug，让整个产线停了半天。嗯，从那以后，我再也不敢轻视测试了。

这一章，我们就来聊聊怎么用Cmock和Ceedling这套工具，给Bootloader做单元测试。说白了，就是让代码自己证明自己是对的。

24.1 为什么Bootloader需要单元测试？

你想想看，Bootloader是系统上电后第一个跑的程序。它挂了，整个设备就变砖了。我见过太多项目，Bootloader代码写完了，全靠硬件工程师拿示波器在那点来点去。这哪是测试？这是碰运气。

单元测试能帮你做到三件事：

  • 早期发现问题——编译完就能跑测试，不用等硬件就绪
  • 回归保护——改了一行代码，跑一遍测试就知道有没有破坏原有逻辑
  • 文档化行为——测试用例本身就是最好的使用说明

核心观点：没有单元测试的Bootloader，就像没有安全带的赛车。跑得快，但出事也快。

24.2 Ceedling + Cmock：嵌入式测试的黄金搭档

Ceedling本质上是一个构建系统，它把Unity（测试框架）和Cmock（模拟框架）整合在了一起。我个人习惯用Ceedling来管理整个测试工程，因为它自动帮你处理了编译、链接、运行这些杂事。

24.2.1 安装与初始化

安装其实很简单，Ruby环境配好之后，一行命令就搞定：

gem install ceedling

然后在你Bootloader工程的根目录下跑：

ceedling new bootloader_test

这会生成一个测试工程目录，结构大概是这样：

bootloader_test/
├── src/          # 放你的源代码
├── test/         # 放测试用例
├── lib/          # 放依赖库
└── project.yml   # 配置文件

我记得第一次用的时候，觉得这目录结构有点死板。后来用习惯了才发现，这种约定优于配置的方式，反而让团队协作变得简单了。

24.2.2 Cmock的核心思想

Cmock是用来做模拟的。什么叫模拟？就是当你的代码调用了一个外部函数（比如Flash读写函数），测试框架可以「假装」这个函数存在，并且控制它的返回值。

举个例子，你的Bootloader里有一段代码要擦除Flash扇区：

// flash_driver.c
int flash_erase_sector(uint32_t addr) {
    // 调用底层硬件操作
    return HAL_FLASH_Erase(addr);
}

// bootloader.c
int update_firmware(void) {
    if (flash_erase_sector(0x08010000) != 0) {
        return -1;  // 擦除失败
    }
    // 继续写数据...
    return 0;
}

在真实硬件上测试update_firmware，你得先有一块板子，还得担心擦坏了什么。用Cmock，你可以这样测：

// test_bootloader.c
#include "unity.h"
#include "mock_flash_driver.h"

void test_update_firmware_erase_fail(void) {
    // 设置模拟：让flash_erase_sector返回-1
    flash_erase_sector_ExpectAndReturn(0x08010000, -1);
    
    // 调用被测函数
    int result = update_firmware();
    
    // 验证结果
    TEST_ASSERT_EQUAL(-1, result);
}

void test_update_firmware_success(void) {
    // 设置模拟：让flash_erase_sector返回0
    flash_erase_sector_ExpectAndReturn(0x08010000, 0);
    
    int result = update_firmware();
    
    TEST_ASSERT_EQUAL(0, result);
}

小技巧：Cmock会自动检查函数调用顺序和参数。如果被测代码调用了flash_erase_sector两次，但你只设置了一次Expect，测试就会失败。这个特性在调试复杂状态机时特别有用。

24.3 Flash驱动模拟测试：一个实战案例

Flash驱动是Bootloader里最容易出问题的地方。我曾经遇到过一个坑：某款Flash芯片在连续擦写时，需要插入延时。代码里没加，结果跑了几百次后，突然有一次写进去的数据全是0xFF。

这种问题在硬件上复现很难，但用模拟测试可以轻松覆盖。

24.3.1 设计可测试的Flash驱动

要让Flash驱动可测试，关键是把硬件操作抽象出来。我一般会这样做：

// flash_driver.h
typedef struct {
    int (*init)(void);
    int (*erase)(uint32_t addr);
    int (*write)(uint32_t addr, const uint8_t* data, uint32_t len);
    int (*read)(uint32_t addr, uint8_t* data, uint32_t len);
} flash_ops_t;

// 外部接口
int flash_init(const flash_ops_t* ops);
int flash_erase_sector(uint32_t addr);
int flash_write_page(uint32_t addr, const uint8_t* data, uint32_t len);

这样设计的好处是，测试时可以传入一个模拟的ops结构体，完全控制Flash的行为。

24.3.2 模拟测试用例

我们来写几个关键的测试用例：

// test_flash_driver.c
#include "unity.h"
#include "mock_flash_ops.h"

static flash_ops_t test_ops;

void setUp(void) {
    // 每个测试前重置模拟
    test_ops.init = flash_init_Stub;
    test_ops.erase = flash_erase_Stub;
    test_ops.write = flash_write_Stub;
    test_ops.read = flash_read_Stub;
}

void test_flash_erase_retry_on_timeout(void) {
    // 模拟前两次擦除超时，第三次成功
    flash_erase_StubWithReturn(0x08010000, -1);
    flash_erase_StubWithReturn(0x08010000, -1);
    flash_erase_StubWithReturn(0x08010000, 0);
    
    int result = flash_erase_sector(0x08010000);
    TEST_ASSERT_EQUAL(0, result);
}

void test_flash_write_verify_fail(void) {
    // 模拟写入成功但校验失败
    flash_write_StubWithReturn(0x08020000, test_data, 256, 0);
    flash_read_StubWithReturn(0x08020000, corrupted_data, 256, 0);
    
    int result = flash_write_page(0x08020000, test_data, 256);
    TEST_ASSERT_EQUAL(-2, result);  // 校验失败错误码
}

注意：模拟测试只能验证逻辑正确性，不能替代硬件测试。Flash的时序特性、电压波动等物理问题，还是得在真实硬件上验证。我的做法是：单元测试覆盖90%的逻辑路径，硬件测试覆盖边界条件和异常场景。

24.4 通信协议测试：让数据说话

Bootloader的通信协议，比如XMODEM、YMODEM或者自定义的升级协议，是另一个测试重点。这类协议通常有复杂的握手、校验和重传机制。

24.4.1 模拟通信层

通信协议的测试，核心是模拟底层收发接口。我一般会这样抽象：

// comm_driver.h
typedef struct {
    int (*send)(const uint8_t* data, uint32_t len);
    int (*receive)(uint8_t* data, uint32_t timeout_ms);
} comm_ops_t;

测试时，我们可以模拟各种网络状况：

// test_xmodem.c
#include "unity.h"
#include "mock_comm_driver.h"

void test_xmodem_normal_transfer(void) {
    // 模拟正常接收流程
    // 发送NAK请求
    comm_send_Expect(NAK, 1);
    // 接收第一个数据包
    comm_receive_ExpectAndReturn(test_packet, 133, 133);
    // 发送ACK确认
    comm_send_Expect(ACK, 1);
    
    int result = xmodem_receive();
    TEST_ASSERT_EQUAL(0, result);
}

void test_xmodem_retry_on_crc_error(void) {
    // 模拟CRC错误
    comm_send_Expect(NAK, 1);
    comm_receive_ExpectAndReturn(corrupted_packet, 133, 133);
    // 发送NAK请求重传
    comm_send_Expect(NAK, 1);
    comm_receive_ExpectAndReturn(correct_packet, 133, 133);
    comm_send_Expect(ACK, 1);
    
    int result = xmodem_receive();
    TEST_ASSERT_EQUAL(0, result);
}

void test_xmodem_timeout_handling(void) {
    // 模拟接收超时
    comm_send_Expect(NAK, 1);
    comm_receive_ExpectAndReturn(NULL, 0, -1);  // 超时返回-1
    
    // 重试3次后放弃
    comm_send_Expect(NAK, 1);
    comm_receive_ExpectAndReturn(NULL, 0, -1);
    comm_send_Expect(NAK, 1);
    comm_receive_ExpectAndReturn(NULL, 0, -1);
    
    int result = xmodem_receive();
    TEST_ASSERT_EQUAL(-3, result);  // 超时错误码
}

24.4.2 测试覆盖率分析

Ceedling自带覆盖率分析工具。跑完测试后，执行：

ceedling gcov:all

它会生成一个HTML报告，告诉你哪些代码行被测试覆盖了，哪些没有。我个人习惯把覆盖率目标定在80%以上，核心逻辑（比如状态机、错误处理）要求100%。

模块 行覆盖率 分支覆盖率 备注
Flash驱动 92% 88% 硬件初始化部分未覆盖
XMODEM协议 96% 94% 所有状态机路径已覆盖
CRC校验 100% 100% 边界值测试通过

24.5 持续集成中的测试实践

测试写好了，怎么让它持续发挥作用？我的建议是集成到CI流水线中。每次提交代码，自动跑一遍所有测试。

Ceedling支持命令行模式，非常适合CI：

# Jenkins/GitLab CI脚本
ceedling clean
ceedling test:all
ceedling gcov:all

如果测试失败，CI直接报红，开发者必须修复才能合并。这个流程看起来简单，但能拦住90%的回归问题。

我的经验：刚开始推行单元测试时，团队阻力很大，觉得浪费时间。后来我定了个规矩：新代码必须带测试，旧代码逐步补。三个月后，Bug率下降了60%。从那以后，没人再质疑测试的价值了。

24.6 本章小结

单元测试不是银弹，但它确实是Bootloader开发中性价比最高的质量保障手段。Ceedling和Cmock这套组合，让嵌入式测试变得不再痛苦。

记住几个要点：

  • 用Ceedling管理测试工程，省心省力
  • Cmock模拟外部依赖，让测试脱离硬件
  • Flash驱动和通信协议是测试重点
  • 覆盖率80%是底线，核心逻辑要100%
  • 集成到CI中，让测试自动化运行
