第二十八讲：量产烧录方案

量产烧录，说白了就是工厂里怎么把固件灌进去，还要把序列号、校准参数这些“身份证”信息写对。我见过太多研发样机跑得飞起，一到产线就翻车的案例。嗯，今天咱们就把这块硬骨头啃下来。

工厂烧录流程设计

先说说整体流程。我个人习惯把量产烧录分成三个阶段：准备阶段、烧录阶段、验证阶段。

准备阶段

这个阶段主要做三件事：

  • 固件打包：把Bootloader、应用程序、校准参数模板打包成一个镜像文件。我建议用CRC32或SHA256做完整性校验。
  • 烧录工具准备：根据芯片接口选择烧录器。SWD、JTAG、UART是主流。我遇到过用USB批量烧录的，速度确实快，但稳定性要仔细调。
  • 工位配置：每个工位要配好电源、烧录器、夹具。我曾经见过一个产线，因为夹具接触不良，烧录成功率只有70%。后来换了镀金探针，问题就解决了。

烧录阶段

这个阶段是核心。流程大概是：

  1. 上电检测：检查芯片是否正常启动。
  2. 擦除Flash：把旧数据清干净。
  3. 写入Bootloader：先写引导程序。
  4. 写入应用程序：再写主程序。
  5. 写入配置数据：序列号、校准参数等。
  6. 校验：读回数据做比对。

关键点：烧录顺序不能乱。先写Bootloader再写App，否则芯片可能变砖。我有个朋友就是先写App再写Bootloader，结果Bootloader写一半断电了，整批板子都得返工。

验证阶段

烧录完不等于完事。必须做验证：

  • CRC校验：对比烧录前后的CRC值。
  • 功能测试：比如让LED闪几下，或者输出特定信号。
  • 序列号唯一性检查：防止重复。

序列号写入

序列号这东西，看着简单，坑不少。我来说说怎么设计。

序列号格式

我建议用这种格式：

typedef struct {
    uint8_t  year;      // 年份，比如0x18表示2018年
    uint8_t  month;     // 月份
    uint8_t  day;       // 日期
    uint8_t  line;      // 产线编号
    uint16_t seq;       // 当日序号
    uint8_t  checksum;  // 校验和
} SerialNumber_t;

为什么这么设计？你想想看，如果哪天发现某批产品有问题，通过序列号就能快速定位到是哪天、哪条产线生产的。我在项目中就靠这个追回过一批有问题的货。

写入位置

序列号一般存在Flash的末尾区域。我习惯这样分配：

区域 起始地址 大小 内容
Bootloader 0x08000000 32KB 引导程序
App 0x08008000 448KB 应用程序
Config 0x0807E000 4KB 校准参数
Serial 0x0807F000 4KB 序列号

小技巧：序列号区域可以多留几份备份。比如写3份，读的时候用“三取二”策略。这样即使某份数据损坏，还能恢复。

写入流程

实际写入时要注意：

  1. 先读当前序列号，防止重复写入。
  2. 生成新序列号，计算校验和。
  3. 擦除Flash扇区。
  4. 写入数据。
  5. 读回验证。
// 伪代码示例
uint8_t WriteSerialNumber(SerialNumber_t *sn) {
    // 1. 检查是否已写入
    if (ReadSerialNumber(&old_sn) == SUCCESS) {
        return ALREADY_WRITTEN;
    }
    
    // 2. 计算校验和
    sn->checksum = CalculateChecksum(sn);
    
    // 3. 擦除扇区
    FlashErase(SERIAL_SECTOR);
    
    // 4. 写入三份备份
    for (int i = 0; i < 3; i++) {
        FlashWrite(SERIAL_ADDR + i * sizeof(SerialNumber_t), sn);
    }
    
    // 5. 验证
    return VerifySerialNumber(sn);
}

校准参数存储

校准参数比序列号复杂。每个设备的校准值都不一样，比如ADC偏移量、温度传感器系数等。

存储结构

我建议用键值对的方式存储：

typedef struct {
    uint16_t key;       // 参数ID
    uint16_t length;    // 数据长度
    uint8_t  data[64];  // 参数值
    uint16_t crc;       // CRC校验
} CalibrationItem_t;

为什么用键值对？因为不同产品需要的校准参数不一样。有的需要3个，有的需要10个。用键值对可以灵活扩展。

写入策略

校准参数写入要注意几点：

  • 原子操作：要么全部写入成功，要么全部回滚。我遇到过写入一半断电，参数损坏的情况。
  • 版本管理：给校准数据加个版本号。这样升级固件时，能知道旧参数是否兼容。
  • 备份机制：至少保留一份有效备份。我习惯用A/B分区，一个区写坏了，自动切到另一个区。

避坑指南：我曾经遇到过一批产品，校准参数写入后，过几天就丢失了。查了半天，发现是Flash的写寿命问题。校准参数频繁擦写，把Flash写坏了。后来我改用EEPROM模拟，或者加磨损均衡算法，问题就解决了。

产线校准流程

实际产线上，校准流程一般是：

  1. 设备上电，进入校准模式。
  2. 产线电脑发送校准指令。
  3. 设备采集标准信号，计算校准值。
  4. 设备把校准值写入Flash。
  5. 设备读回校准值，验证正确性。
  6. 产线电脑记录校准结果。

这里有个细节：校准过程中，设备不能断电。我建议在硬件上加个电容，保证掉电后还能维持几十毫秒，让写入操作完成。

量产烧录的常见问题

最后，我总结几个量产烧录的常见坑：

  • 烧录速度慢：单个设备烧录时间太长，影响产能。我建议用多路并行烧录，或者用高速接口。
  • 烧录不稳定：接触不良、电源噪声都可能导致烧录失败。夹具和电源质量不能省。
  • 数据一致性：同一批产品，校准参数格式必须统一。我建议用配置文件管理参数定义。
  • 防呆设计：防止操作员把固件烧错。比如加个产品ID校验，ID不对就不让烧。

核心思想：量产烧录不是写代码，是设计流程。流程设计好了，产线才能跑得顺。我见过太多研发人员，代码写得漂亮，但量产方案一塌糊涂。记住，量产烧录的目标是：快、稳、准。
