第三十章：项目实战：从零构建一个完整的Bootloader项目

终于到了最后一章。说实话，写到这里我挺感慨的。前面二十九章我们聊了那么多理论、协议、芯片细节，但真正把知识串起来，还得靠一个完整的项目。

这一章，我们就从零开始，做一个真正的Bootloader。不是玩具，是能用在产品上的那种。

30.1 需求分析：先搞清楚要做什么

做项目最怕什么？最怕需求没想清楚就开干。我见过太多团队，代码写了一半才发现「哦，原来还要支持这个功能」。嗯，返工的滋味可不好受。

我们这个Bootloader，目标平台是STM32F407，需求如下：

  • 支持串口Ymodem协议升级：这是最常用的方式，稳定可靠
  • 支持固件校验：CRC32校验，防止传输错误
  • 支持回滚机制：升级失败能自动恢复旧版本
  • 看门狗保护：防止升级过程中死机
  • 启动超时：如果用户不干预，自动跳转应用程序
  • Flash分区管理：Bootloader、应用程序A、应用程序B三个区

Flash分区规划：

分区起始地址大小说明
Bootloader0x0800000064KB存放Bootloader代码
App A0x08010000256KB主应用程序区
App B0x08050000256KB备份应用程序区
参数区0x080900004KB存放升级标志、版本号等

为什么分两个应用区？说白了就是为了安全。升级时把新固件写到App B，校验通过后再把App B复制到App A。万一断电了，App A还是好的，系统照样能跑。

30.2 架构设计：画好图纸再动工

我个人习惯，写代码前先画流程图。别嫌麻烦，这一步能省后面80%的调试时间。

Bootloader的主流程其实很简单：

  1. 系统上电，初始化时钟、串口、看门狗
  2. 检查是否有升级请求（按键、串口命令、标志位）
  3. 如果有升级请求，进入升级模式
  4. 如果没有，检查App A是否有效
  5. 如果App A有效，跳转执行
  6. 如果App A无效，尝试恢复App B
  7. 都无效，进入DFU模式等待用户干预

这里有个关键点：跳转前一定要关中断。我在项目中遇到过，跳转时没关SysTick中断，结果应用程序里中断向量表还没初始化，直接跑飞了。那次排查了整整两天。

30.3 编码实现：动手写代码

好，图纸画完了，咱们开始砌砖。我会挑核心代码讲，完整的工程文件在课程资料里。

30.3.1 启动流程

void bootloader_main(void)
{
    /* 初始化硬件 */
    system_init();          // 时钟、GPIO、串口
    watchdog_init(5000);    // 5秒看门狗
    
    /* 检查升级请求 */
    if (check_update_request())
    {
        /* 进入升级模式 */
        update_firmware();
    }
    else
    {
        /* 检查App A有效性 */
        if (check_app_valid(APP_A_ADDR))
        {
            /* 跳转到App A */
            jump_to_app(APP_A_ADDR);
        }
        else
        {
            /* 尝试恢复App B */
            if (restore_from_backup())
            {
                jump_to_app(APP_A_ADDR);
            }
            else
            {
                /* 都失败了，进入DFU模式 */
                enter_dfu_mode();
            }
        }
    }
    
    /* 正常情况下不会执行到这里 */
    while(1);
}

你看，主函数其实很简洁。真正的复杂度都在各个子函数里。

30.3.2 Ymodem接收实现

Ymodem协议说白了就是：发送方先发文件名和大小，然后一块一块发数据，每块128字节。接收方每收到一块，回一个ACK。

int ymodem_receive(uint32_t flash_addr)
{
    uint8_t buffer[128];
    uint16_t crc;
    uint32_t offset = 0;
    uint32_t file_size = 0;
    
    /* 第一步：接收文件头 */
    if (ymodem_recv_packet(buffer, &crc) != 0)
        return -1;
    
    /* 解析文件名和大小 */
    file_size = parse_file_info(buffer);
    
    /* 第二步：接收数据块 */
    while (offset < file_size)
    {
        if (ymodem_recv_packet(buffer, &crc) != 0)
            return -2;
        
        /* 写入Flash */
        flash_write(flash_addr + offset, buffer, 128);
        offset += 128;
        
        /* 喂狗，防止升级过程中超时复位 */
        watchdog_feed();
    }
    
    /* 第三步：接收结束包 */
    ymodem_recv_eot();
    
    return 0;
}

小技巧：Ymodem接收时，每写一块Flash就喂一次看门狗。我曾经遇到过，升级大固件时忘了喂狗，写到一半系统复位了，那叫一个惨。后来我养成了习惯：任何耗时操作里都要喂狗。

30.3.3 CRC32校验

固件传输完了，得检查对不对。CRC32是个好选择，速度快，碰撞概率低。

uint32_t calculate_crc32(uint32_t addr, uint32_t size)
{
    uint32_t crc = 0xFFFFFFFF;
    uint8_t data;
    
    for (uint32_t i = 0; i < size; i++)
    {
        data = *(volatile uint8_t*)(addr + i);
        crc = crc32_table[(crc ^ data) & 0xFF] ^ (crc >> 8);
    }
    
    return crc ^ 0xFFFFFFFF;
}

int verify_firmware(uint32_t addr, uint32_t size, uint32_t expected_crc)
{
    uint32_t actual_crc = calculate_crc32(addr, size);
    return (actual_crc == expected_crc) ? 0 : -1;
}

30.3.4 跳转实现

跳转这部分，说白了就是修改栈指针和程序计数器。但细节决定成败。

void jump_to_app(uint32_t app_addr)
{
    uint32_t stack_ptr;
    void (*app_entry)(void);
    
    /* 读取应用程序的栈指针 */
    stack_ptr = *(volatile uint32_t*)app_addr;
    
    /* 读取应用程序的入口地址 */
    app_entry = (void (*)(void))(*(volatile uint32_t*)(app_addr + 4));
    
    /* 关全局中断 */
    __disable_irq();
    
    /* 关SysTick */
    SysTick->CTRL = 0;
    
    /* 清理所有挂起的中断 */
    for (int i = 0; i < 8; i++)
    {
        NVIC->ICER[i] = 0xFFFFFFFF;
        NVIC->ICPTR[i] = 0xFFFFFFFF;
    }
    
    /* 设置新的栈指针 */
    __set_MSP(stack_ptr);
    
    /* 跳转 */
    app_entry();
}

警告：跳转前一定要把所有外设恢复到复位状态。我见过有人忘了关DMA，跳转后DMA还在传输，直接把应用程序的内存写乱了。这种bug极难排查，因为问题出现的时间点是随机的。

30.4 测试验证：别让bug上线

代码写完了，怎么测？我一般分四步走：

30.4.1 单元测试

先测每个函数单独能不能跑。比如CRC32计算，我写个测试用例，输入已知数据，比对结果对不对。Flash读写也要单独测，确保地址没错。

30.4.2 功能测试

把Bootloader烧进去，然后通过串口发一个固件。看看能不能正常升级、正常跳转。这里要测几个边界情况：

  • 固件大小刚好是128的整数倍
  • 固件大小不是128的整数倍（需要填充）
  • 固件CRC错误（应该拒绝升级）
  • 升级过程中断电（重启后应该能恢复）

30.4.3 压力测试

连续升级100次，看看会不会出问题。我遇到过，有些Flash芯片写多了会变慢，导致看门狗超时。这种问题只有压力测试才能发现。

30.4.4 异常测试

人为制造各种异常：

  • 串口线在升级过程中拔掉
  • 发送错误的数据包
  • 故意让CRC校验失败
  • 在跳转瞬间复位

嗯，这些测试都通过了，才能说这个Bootloader是可靠的。

30.5 避坑指南

最后，分享几个我踩过的坑：

  • 中断向量表偏移：应用程序里一定要设置SCB->VTOR，否则中断来了找不到入口。这个坑我踩了三次才记住。
  • Flash写入对齐：STM32的Flash写入要求16字节对齐，不对齐会HardFault。我建议统一按16字节处理。
  • 看门狗时间：升级大固件时，擦除Flash很耗时。我一般把看门狗设到10秒，留足余量。
  • 串口缓冲区：Ymodem是半双工协议，接收缓冲区至少256字节。太小了容易丢包。

好了，到这里，我们的Bootloader项目就完整了。从需求分析到架构设计，从编码实现到测试验证，每一步都走了一遍。

说实话，做一个能用的Bootloader不难，但做一个可靠的Bootloader，需要细心和耐心。希望这门课能帮你少走一些弯路。
