第9章：固件包格式设计

各位同学，今天我们来聊聊固件包格式设计。说实话，这个章节在Bootloader开发中特别容易被忽视。很多人觉得「不就是把二进制文件打包一下嘛」，结果在实际项目中踩了不少坑。我自己就见过因为固件格式设计不合理，导致产线升级失败率高达30%的案例。

9.1 固件头结构定义

固件头，说白了就是固件包的「身份证」。Bootloader拿到一个固件包，首先要读的就是这个头。它告诉Bootloader：你是谁、多大、用什么算法校验、该烧到哪个地址。

我个人习惯把固件头设计成固定长度，通常是64字节或128字节。为什么？因为固定长度好解析，Bootloader不用猜。你想想看，如果头长度可变，Bootloader还得先读4字节知道头有多长，再读剩下的，多了一步操作，在资源受限的MCU上这就是浪费。

下面是我在项目中常用的一种固件头结构：

typedef struct {
    uint32_t magic;          // 魔数，用于识别固件合法性
    uint32_t header_crc;     // 固件头自身的CRC
    uint32_t firmware_crc;   // 固件数据的CRC
    uint32_t firmware_size;  // 固件数据大小（不含头）
    uint32_t load_address;   // 加载地址
    uint32_t entry_point;    // 入口地址
    uint8_t  version_major;  // 主版本号
    uint8_t  version_minor;  // 次版本号
    uint8_t  version_patch;  // 补丁版本号
    uint8_t  encryption_type;// 加密类型：0=无，1=AES，2=RSA
    uint8_t  signature_type; // 签名类型：0=无，1=HMAC，2=RSA
    uint8_t  reserved[38];   // 保留字段，对齐到64字节
} firmware_header_t;

关键字段说明：

  • magic：我习惯用0xDEADBEEF或者0xA5A5A5A5，别用太常见的值，防止误识别
  • header_crc：只校验固件头本身，确保头没被篡改
  • firmware_crc：校验整个固件数据区，这个最重要
  • reserved：一定要留保留字段！我曾经吃过亏，后来加功能时发现头长度不够，只能改版本号兼容

9.2 CRC校验算法实现

CRC校验是固件完整性检查的基石。市面上有很多CRC变种，CRC32、CRC16、CRC8，选哪个？我的建议是：MCU资源允许就用CRC32。为什么？碰撞概率低，安全性相对好。

嗯，这里要注意一点：CRC不是加密算法，它只是检错码。如果有人故意篡改固件，CRC是防不住的。但作为传输过程中的误码检测，它足够了。

下面是我常用的CRC32实现，查表法，速度很快：

// CRC32查表法实现
static uint32_t crc32_table[256];

void crc32_init_table(void) {
    for (uint32_t i = 0; i < 256; i++) {
        uint32_t crc = i;
        for (int j = 0; j < 8; j++) {
            if (crc & 1)
                crc = (crc >> 1) ^ 0xEDB88320;
            else
                crc >>= 1;
        }
        crc32_table[i] = crc;
    }
}

uint32_t crc32_calculate(const uint8_t *data, uint32_t len) {
    uint32_t crc = 0xFFFFFFFF;
    for (uint32_t i = 0; i < len; i++) {
        uint8_t index = (crc ^ data[i]) & 0xFF;
        crc = (crc >> 8) ^ crc32_table[index];
    }
    return crc ^ 0xFFFFFFFF;
}

避坑指南：我曾经在项目中直接用网上找的CRC代码，结果没注意初始值和异或值，跟上位机算出来的对不上。排查了两天才发现是多项式初始值不一致。所以，上位机和下位机必须用同一套CRC参数，包括多项式、初始值、结果异或值、输入输出反转。

9.3 固件加密与签名基础

讲到这里，我得说句实话：很多嵌入式产品其实不需要加密。为什么？因为攻击者拿到固件也没用，硬件绑定了。但如果你做的是物联网设备、金融终端、或者车规级产品，那加密和签名就是刚需。

加密和签名的区别，我用一句话说清楚：加密是防止别人看到内容，签名是防止别人篡改内容。两者可以同时使用，也可以只用签名。

9.3.1 对称加密：AES

AES是目前最常用的对称加密算法。在Bootloader场景下，我推荐使用AES-128-CBC模式。为什么是128？因为256对MCU来说计算量太大，128已经足够安全。CBC模式需要IV向量，每次加密用随机IV，这样同样的固件每次加密结果都不同。

// AES-128-CBC解密示例（使用mbedTLS库）
#include "mbedtls/aes.h"

int firmware_decrypt(uint8_t *data, uint32_t len, 
                     const uint8_t *key, const uint8_t *iv) {
    mbedtls_aes_context aes;
    mbedtls_aes_init(&aes);
    
    mbedtls_aes_setkey_dec(&aes, key, 128);
    
    // 注意：len必须是16的倍数
    mbedtls_aes_crypt_cbc(&aes, MBEDTLS_AES_DECRYPT, 
                          len, iv, data, data);
    
    mbedtls_aes_free(&aes);
    return 0;
}

重要提醒：密钥怎么存？千万别硬编码在代码里！我见过太多产品，密钥明文写在Flash里，用调试器一读就出来了。建议用芯片的OTP区域或者安全元件存储密钥，或者用密钥派生机制，从芯片唯一ID生成密钥。

9.3.2 非对称签名：RSA

签名我推荐用RSA-2048。虽然计算慢，但安全性高。实际项目中，我们通常这样配合使用：

  1. 上位机用私钥对固件哈希值签名
  2. Bootloader用公钥验证签名
  3. 公钥固化在Bootloader代码中

这样做的好处是：私钥泄露了可以换，公钥在Bootloader里改不了。你想想看，如果攻击者想伪造固件，他得先拿到私钥，还得破解Bootloader里的公钥，难度大多了。

// RSA签名验证流程（伪代码）
int verify_firmware_signature(firmware_header_t *header, 
                               uint8_t *firmware_data) {
    // 1. 计算固件数据的SHA256哈希
    uint8_t hash[32];
    sha256_calculate(firmware_data, header->firmware_size, hash);
    
    // 2. 从固件头中提取签名
    uint8_t signature[256]; // RSA-2048签名长度
    memcpy(signature, firmware_data + header->firmware_size, 256);
    
    // 3. 用公钥验证签名
    return rsa_verify_signature(public_key, hash, signature);
}

9.4 固件包整体结构

把上面这些组合起来，一个完整的固件包长这样：

偏移 内容 大小
0x0000 固件头（firmware_header_t） 64字节
0x0040 固件数据（加密或明文） 可变
末尾 RSA签名（256字节） 256字节

我的建议流程：

  1. 上位机先计算固件数据的SHA256哈希
  2. 用私钥对哈希签名，追加到固件包末尾
  3. 可选：用AES密钥加密固件数据
  4. 计算整个固件包的CRC32，填入固件头
  5. Bootloader收到后，先校验CRC，再解密，最后验签

最后说一句，固件包格式设计没有银弹。你得根据产品需求来权衡：安全等级、MCU性能、升级时间、产线效率。我个人建议，先从签名做起，加密可以后续再加。因为签名能防篡改，这是最基础的安全需求。加密嘛，等你产品卖到一定量级再考虑也不迟。
