第19章 命令行接口(CLI)开发：CLI框架设计、命令解析器实现、调试命令扩展

说到Bootloader的调试，我最常用的工具就是命令行接口。你想想看，一个嵌入式系统刚上电，没有操作系统，没有图形界面，你怎么跟它交互？串口命令行就是最直接的方式。我在做第一个Bootloader项目时，就深刻体会到了CLI的重要性——没有它，调试就像在黑暗中摸索。

19.1 CLI框架设计

CLI框架说白了就是一套"命令处理流水线"。它要完成三件事：接收输入、解析命令、执行动作。我习惯把框架分成三层：

  • 输入层：负责从串口读取字符，处理回显、退格等基础操作
  • 解析层：将字符串拆解成命令和参数
  • 执行层：根据解析结果调用对应的处理函数

先看一个最简的框架设计：

/* CLI命令结构体 */
typedef struct {
    const char *name;        /* 命令名称 */
    const char *help;        /* 帮助信息 */
    int (*handler)(int argc, char *argv[]);  /* 处理函数 */
} cli_cmd_t;

/* CLI控制块 */
typedef struct {
    char rx_buf[256];        /* 接收缓冲区 */
    uint16_t rx_len;         /* 已接收长度 */
    cli_cmd_t *cmd_table;    /* 命令表 */
    uint32_t cmd_count;      /* 命令数量 */
} cli_ctrl_t;

嗯，这里要注意缓冲区大小。我遇到过有人只给32字节，结果一条长命令直接溢出，系统崩溃。建议至少256字节，如果命令复杂，512字节更稳妥。

19.2 命令解析器实现

命令解析器是CLI的核心。它的工作就是把"erase 0x08010000 0x10000"这样的字符串，解析成argc=3，argv[0]="erase"，argv[1]="0x08010000"，argv[2]="0x10000"。

我个人习惯用空格作为分隔符，简单可靠。解析流程如下：

  1. 跳过行首空白字符
  2. 找到下一个空白字符，截取一个token
  3. 重复直到字符串结束
  4. 统计token数量作为argc
static int cli_parse(char *line, int *argc, char *argv[], int max_args)
{
    char *p = line;
    int count = 0;

    while (*p) {
        /* 跳过空白 */
        while (*p == ' ' || *p == '\t')
            p++;

        if (*p == '\0')
            break;

        if (count >= max_args)
            return -1;  /* 参数太多 */

        argv[count++] = p;

        /* 找到下一个空白 */
        while (*p && *p != ' ' && *p != '\t')
            p++;

        if (*p) {
            *p = '\0';  /* 字符串截断 */
            p++;
        }
    }

    *argc = count;
    return 0;
}

我曾经在解析时犯过一个低级错误——没处理连续空格。结果用户输入"erase 0x08010000 0x10000"（多个空格），解析出来的参数全乱了。所以上面的代码里，我用了两个while循环来跳过空白，确保不管多少个空格都能正确处理。

19.3 命令匹配与执行

解析完成后，就要在命令表中查找匹配的命令。我建议用线性查找，因为Bootloader的命令通常不超过20个，没必要搞哈希表。

static int cli_execute(cli_ctrl_t *ctrl, int argc, char *argv[])
{
    for (uint32_t i = 0; i < ctrl->cmd_count; i++) {
        if (strcmp(argv[0], ctrl->cmd_table[i].name) == 0) {
            return ctrl->cmd_table[i].handler(argc, argv);
        }
    }

    printf("Error: unknown command '%s'\n", argv[0]);
    return -1;
}

这里有个小技巧：支持命令缩写。比如"help"可以缩写成"h"，"erase"缩写成"e"。实现方式很简单，比较时用strncmp代替strcmp，但要注意避免歧义。我建议只对常用命令做缩写，而且缩写长度至少3个字符。

核心要点：命令匹配时，先精确匹配，再尝试模糊匹配。如果模糊匹配有多个结果，报错提示用户。

19.4 调试命令扩展

调试命令是CLI最有价值的部分。我一般会提供以下几类：

命令类别 示例命令 用途
内存操作 md, mw, mm 查看/修改内存内容
Flash操作 erase, write, protect 擦除/写入/保护Flash
寄存器操作 reg, setreg 读写CPU外设寄存器
系统信息 info, version, reset 查看系统状态、重启
测试命令 test_ram, test_flash 硬件自检

以内存显示命令为例，实现起来很直观：

static int cmd_memory_dump(int argc, char *argv[])
{
    uint32_t addr, len;

    if (argc < 3) {
        printf("Usage: md <addr> <len>\n");
        return -1;
    }

    addr = strtoul(argv[1], NULL, 16);
    len  = strtoul(argv[2], NULL, 16);

    for (uint32_t i = 0; i < len; i += 16) {
        printf("%08X: ", addr + i);
        for (int j = 0; j < 16; j++) {
            if (i + j < len)
                printf("%02X ", *(uint8_t *)(addr + i + j));
            else
                printf("   ");
        }
        printf("\n");
    }

    return 0;
}

经验之谈：调试命令一定要加保护。比如内存dump时，如果地址是NULL或者超出RAM范围，直接返回错误。我曾经在客户现场调试，一条"md 0 100"命令直接导致系统挂死——因为地址0是中断向量表，读着读着就触发异常了。

19.5 历史记录与行编辑

一个好用的CLI还得支持历史记录和行编辑。历史记录用环形缓冲区实现，保存最近10-20条命令。行编辑支持退格、左右移动、插入删除。

实现行编辑时，我建议用ANSI转义序列。比如收到0x1B 0x5B 0x41（上箭头），就显示上一条历史命令。代码大概这样：

static void cli_process_char(cli_ctrl_t *ctrl, char ch)
{
    if (ch == '\r' || ch == '\n') {
        /* 回车：执行命令 */
        ctrl->rx_buf[ctrl->rx_len] = '\0';
        cli_add_history(ctrl, ctrl->rx_buf);
        cli_parse_and_execute(ctrl);
        ctrl->rx_len = 0;
        printf("\n> ");
    } else if (ch == 0x1B) {
        /* 转义序列开始，进入转义处理状态 */
        ctrl->state = CLI_ESC;
    } else if (ch == '\b' || ch == 0x7F) {
        /* 退格 */
        if (ctrl->rx_len > 0) {
            ctrl->rx_len--;
            printf("\b \b");
        }
    } else if (ch >= 0x20 && ch <= 0x7E) {
        /* 可打印字符 */
        if (ctrl->rx_len < sizeof(ctrl->rx_buf) - 1) {
            ctrl->rx_buf[ctrl->rx_len++] = ch;
            putchar(ch);
        }
    }
}

注意：转义序列处理是状态机，不要用简单的if-else硬编码。我见过有人用switch-case处理每个字符，结果代码写了一千多行还一堆bug。建议用状态表或者有限状态机库。

19.6 实际项目中的CLI优化

在实际项目中，CLI还需要考虑几个问题：

  • 中断安全：串口接收在中断中，命令解析在主循环中。用环形队列做缓冲，避免中断和主循环竞争。
  • 超时处理：如果用户输入一半不输入了，设置一个超时定时器，超时后清空缓冲区。
  • 命令权限：有些命令（比如Flash擦除）需要用户确认，防止误操作。

我记得有一次，产线工人用CLI批量烧录固件，结果不小心输入了"erase all"命令，整批产品的Flash都被擦空了。从那以后，我所有破坏性操作都加了二次确认：

static int cmd_flash_erase(int argc, char *argv[])
{
    printf("WARNING: This will erase Flash region!\n");
    printf("Type 'yes' to continue: ");

    char response[16];
    if (cli_read_line(response, sizeof(response)) == 0) {
        if (strcmp(response, "yes") != 0) {
            printf("Operation cancelled.\n");
            return 0;
        }
    }

    /* 执行擦除操作 */
    // ...
}

嗯，CLI开发看似简单，但要做好其实不容易。从框架设计到命令解析，再到调试命令扩展，每一步都有坑。我建议你先实现一个最小可用的版本，然后逐步添加功能。记住，CLI是给开发者用的工具，好用比好看更重要。

最后说一句：调试命令一定要留后门。比如加一个隐藏命令"debug_enter"，可以进入更底层的调试模式。我在好几个项目中都用这个方式，在客户现场快速定位问题。当然，这个命令要加编译开关，正式发布时关掉。
