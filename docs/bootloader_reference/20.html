第二十章：日志系统设计：日志级别定义、日志输出接口、Flash日志存储与读取

日志系统，说白了就是Bootloader的“黑匣子”。

我刚开始做Bootloader那会儿，总觉得日志可有可无。直到有一次，产品在客户现场死机了，我连发生了什么都不知道。嗯，从那以后，我再也不敢轻视日志系统了。

今天我们就来聊聊，怎么给Bootloader设计一套靠谱的日志系统。

20.1 日志级别定义

日志级别这东西，说白了就是给信息分个三六九等。我个人习惯用5个级别，从低到高分别是：

级别 数值 含义 使用场景
DEBUG 0 调试信息 开发阶段，打印变量值、函数调用等
INFO 1 普通信息 记录启动流程、版本号等
WARN 2 警告信息 非致命异常，比如校验和错误但还能恢复
ERROR 3 错误信息 功能异常，比如Flash写入失败
FATAL 4 致命错误 系统无法继续运行，比如看门狗超时

核心原则：发布版本只保留WARN及以上级别，DEBUG和INFO在正式固件中关闭。你想想看，如果客户现场满屏都是调试信息，那得多尴尬。

代码实现上，我一般这样定义：

/* 日志级别枚举 */
typedef enum {
    LOG_LEVEL_DEBUG = 0,
    LOG_LEVEL_INFO  = 1,
    LOG_LEVEL_WARN  = 2,
    LOG_LEVEL_ERROR = 3,
    LOG_LEVEL_FATAL = 4
} log_level_t;

/* 当前日志级别，编译时可配置 */
#ifndef LOG_CURRENT_LEVEL
    #define LOG_CURRENT_LEVEL LOG_LEVEL_INFO
#endif

20.2 日志输出接口

接口设计这块，我踩过不少坑。最开始我直接用printf，结果发现重定向到不同设备时，代码改得乱七八糟。

后来我学乖了，用宏封装一层：

/* 日志输出宏 */
#define LOG_DEBUG(fmt, ...) \
    do { \
        if (LOG_CURRENT_LEVEL <= LOG_LEVEL_DEBUG) { \
            log_output(LOG_LEVEL_DEBUG, "[DEBUG] " fmt, ##__VA_ARGS__); \
        } \
    } while(0)

#define LOG_INFO(fmt, ...) \
    do { \
        if (LOG_CURRENT_LEVEL <= LOG_LEVEL_INFO) { \
            log_output(LOG_LEVEL_INFO, "[INFO] " fmt, ##__VA_ARGS__); \
        } \
    } while(0)

/* 类似定义WARN、ERROR、FATAL */

为什么用do-while？因为这样宏展开后，分号不会出问题。我曾经因为这个细节，排查了整整一个下午。

真正的输出函数长这样：

void log_output(log_level_t level, const char *fmt, ...)
{
    va_list args;
    char buffer[256];
    
    /* 获取时间戳 */
    uint32_t timestamp = get_system_tick();
    
    /* 格式化日志内容 */
    va_start(args, fmt);
    vsnprintf(buffer, sizeof(buffer), fmt, args);
    va_end(args);
    
    /* 输出到串口 */
    uart_send_string(buffer);
    
    /* 同时存储到Flash */
    log_store_to_flash(timestamp, level, buffer);
}

小技巧：我习惯在日志里加上时间戳。这样排查问题时，能精确知道每个事件发生的时刻。特别是在分析死机问题时，时间戳就是破案的关键线索。

20.3 Flash日志存储与读取

Flash存储日志，说白了就是把日志写到非易失存储器里。这样即使系统掉电，日志也不会丢。

20.3.1 存储结构设计

我常用的存储结构是这样的：

/* 日志记录头 */
typedef struct {
    uint32_t timestamp;     /* 时间戳 */
    uint8_t  level;         /* 日志级别 */
    uint16_t length;        /* 日志内容长度 */
    uint16_t crc;           /* CRC校验 */
} __attribute__((packed)) log_record_header_t;

/* 日志存储区管理 */
typedef struct {
    uint32_t write_offset;  /* 当前写入位置 */
    uint32_t read_offset;   /* 当前读取位置 */
    uint32_t total_size;    /* 存储区总大小 */
    uint32_t record_count;  /* 记录总数 */
} log_storage_t;

为什么要有CRC？因为Flash本身有比特翻转的风险。我曾经遇到过，日志读到一半数据就错了，加了CRC后，至少能知道数据是不是完整的。

20.3.2 写入流程

写入Flash时，有几个关键点要注意：

  1. 先擦后写：Flash写入前必须擦除，这是硬件特性
  2. 循环覆盖：存储区满了就从头开始覆盖，别让日志撑爆Flash
  3. 原子操作：每条日志的写入要保证完整性
int log_store_to_flash(uint32_t timestamp, log_level_t level, const char *data)
{
    log_record_header_t header;
    uint32_t data_len = strlen(data);
    
    /* 检查剩余空间，不够就擦除旧区域 */
    if (check_remaining_space(data_len + sizeof(header)) != 0) {
        erase_oldest_sector();
    }
    
    /* 填充头部 */
    header.timestamp = timestamp;
    header.level = level;
    header.length = data_len;
    header.crc = calculate_crc((uint8_t*)data, data_len);
    
    /* 写入头部 */
    flash_write(g_storage.write_offset, (uint8_t*)&header, sizeof(header));
    g_storage.write_offset += sizeof(header);
    
    /* 写入数据 */
    flash_write(g_storage.write_offset, (uint8_t*)data, data_len);
    g_storage.write_offset += data_len;
    
    g_storage.record_count++;
    
    return 0;
}

注意：Flash写入时，千万不能断电。我建议在写入前关闭所有中断，写完再恢复。否则写到一半断电，日志就损坏了。

20.3.3 读取与解析

读取日志时，要能遍历所有记录，并且能过滤级别：

int log_read_all(log_level_t min_level)
{
    uint32_t offset = 0;
    log_record_header_t header;
    char data[256];
    
    while (offset < g_storage.total_size) {
        /* 读取头部 */
        flash_read(offset, (uint8_t*)&header, sizeof(header));
        
        /* 检查CRC */
        flash_read(offset + sizeof(header), (uint8_t*)data, header.length);
        if (header.crc != calculate_crc((uint8_t*)data, header.length)) {
            /* CRC错误，跳过这条记录 */
            offset += sizeof(header) + header.length;
            continue;
        }
        
        /* 过滤级别 */
        if (header.level >= min_level) {
            printf("[%u][%d] %s\n", header.timestamp, header.level, data);
        }
        
        offset += sizeof(header) + header.length;
    }
    
    return 0;
}

20.4 实战经验总结

最后，分享几个我在项目中积累的经验：

  • 日志别太多：每条日志控制在128字节以内，太长会影响Flash寿命
  • 加个开关：运行时能动态调整日志级别，方便现场排查问题
  • 定期清理：日志存储区满了，优先删除最旧的日志，别让新日志写不进去
  • 加个看门狗：Flash写入耗时较长，记得喂狗，别让系统复位了

我曾经在一个项目中，因为日志系统设计得不够健壮，导致客户现场出了问题，日志却读不出来。后来我重新设计了这套方案，用了循环覆盖和CRC校验，再也没出过类似问题。

日志系统看似简单，但设计得好，能帮你省下大量排查问题的时间。希望今天的分享对你有帮助。
