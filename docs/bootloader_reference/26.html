第二十六讲：常见问题排查——Bootloader无法启动、固件校验失败、跳转后程序跑飞

做Bootloader开发，说白了就是跟各种“死法”打交道。我做了这么多年，最怕的不是功能做不出来，而是板子焊好、程序烧进去，结果一上电——啥反应没有。

这一讲，咱们就聊聊最常见的三个“翻车现场”：Bootloader起不来、固件校验过不去、跳转后程序飞了。每个问题我都踩过坑，今天把经验全倒出来。

一、Bootloader无法启动

板子上电，LED不闪，串口没输出。嗯，这情况我遇到过不下十次。别慌，先按顺序排查。

1. 硬件层面的“隐形杀手”

先看电源。我有个血的教训——有一次折腾了两天，最后发现是LDO输出电容焊反了，纹波太大导致MCU上电时序不对。你想想看，Bootloader代码还没跑起来，电源就不干净，后面全白搭。

检查清单：

  • 供电电压：用示波器看启动瞬间的电压跌落。有些MCU在3.3V以下就罢工了。
  • 复位引脚：我习惯在复位脚上挂个10k上拉电阻，再加个100nF电容到地。别省这个电容，否则上电瞬间复位脚毛刺能让你怀疑人生。
  • 时钟源：外部晶振起振了吗？示波器探头点一下OSC脚。如果用的是内部RC，确认配置没错。
⚠️ 特别注意： 有些MCU的BOOT引脚有内部上拉/下拉，但外部电路如果接了强上拉，会覆盖内部配置。我曾经因为BOOT0引脚上多焊了个10k电阻，导致芯片死活进不了系统Bootloader。

2. 启动配置“张冠李戴”

很多MCU有多个启动区域：主Flash、系统Bootloader、SRAM。检查一下：

  • BOOT0/BOOT1引脚电平对不对？
  • Option Bytes（选项字节）有没有被意外修改？
  • Flash的起始地址有没有被擦除？

我个人习惯，在Bootloader最开始的地方放一段“心跳灯”代码——哪怕系统还没初始化完，先让一个GPIO输出方波。这样至少能确认MCU在跑。

// 最简单的“我还活着”检测
void early_init(void) {
    // 先别管时钟配置，直接用默认时钟
    GPIOA->CRL = 0x33333333;  // 推挽输出50MHz
    while(1) {
        GPIOA->BSRR = GPIO_Pin_0;  // 亮
        delay_rough(100000);
        GPIOA->BRR = GPIO_Pin_0;   // 灭
        delay_rough(100000);
    }
}

如果连这个都不亮，那基本可以确定是硬件问题或者芯片根本没跑起来。

二、固件校验失败

Bootloader起来了，串口也打印了“开始校验”，然后给你来一句“Checksum Error”。

为什么会这样？我总结了几种常见情况。

1. 校验算法不匹配

最常见的问题——上位机用的CRC32，Bootloader里算的是CRC16。或者多项式、初始值、输出异或值不一样。

我建议：

  • 上位机和Bootloader用同一套代码库里的CRC函数
  • 测试时先用全0xFF、全0x00的数据块验证
  • 打印出计算过程中的中间值，跟上位机比对
💡 小技巧： 我习惯在固件包的末尾附加一个“校验头”，里面不光有CRC值，还有固件长度、版本号、目标芯片ID。这样Bootloader可以一次性验证多个维度。

2. 传输过程丢包或错位

用串口升级时，波特率越高越容易丢包。我遇到过9600波特率稳如老狗，115200就时不时校验失败。

排查方法：

  • 在Bootloader里把收到的每个字节都打印出来（调试阶段）
  • 对比上位机发送的原始数据，看有没有错位
  • 检查流控（硬件流控还是软件XON/XOFF）

嗯，这里要注意：有些USB转串口芯片在高速下会丢数据。我后来养成了习惯——量产固件升级统一用57600波特率，不高不低，稳。

3. Flash写入问题

校验失败还有一种可能——数据写进Flash后读出来变了。这通常是因为：

  • Flash写入前没有擦除（很多MCU要求先擦后写）
  • 写入地址越界了，覆盖了Bootloader自身
  • Flash的等待周期设置不对，读出来全是乱码
// 一个典型的Flash写入流程（伪代码）
uint32_t write_flash(uint32_t addr, uint8_t *data, uint32_t len) {
    // 1. 解锁Flash
    FLASH->KEYR = 0x45670123;
    FLASH->KEYR = 0xCDEF89AB;
    
    // 2. 擦除扇区（必须！）
    FLASH->SR |= FLASH_SR_EOP;  // 清除标志
    FLASH->CR |= FLASH_CR_PER;  // 页擦除模式
    FLASH->AR = addr;           // 设置地址
    FLASH->CR |= FLASH_CR_STRT; // 开始擦除
    while(!(FLASH->SR & FLASH_SR_EOP)); // 等待完成
    
    // 3. 写入数据
    for(uint32_t i = 0; i < len; i += 2) {
        while(!(FLASH->SR & FLASH_SR_EOP));
        *(volatile uint16_t*)(addr + i) = *(uint16_t*)(data + i);
    }
    
    // 4. 读出验证
    if(memcmp((void*)addr, data, len) != 0) {
        return FLASH_ERROR_VERIFY;
    }
    return FLASH_OK;
}
🔑 关键点： 写入后一定要做读出验证。我见过Flash写入时电压不稳导致数据写偏的案例，不验证根本发现不了。

三、跳转后程序跑飞

校验通过了，Bootloader也跳转到应用程序了，结果程序跑飞——要么进HardFault，要么啥反应没有。

这个问题我调试过最久的一次，花了整整三天。最后发现原因简单得可笑。

1. 中断向量表没重映射

这是最最最常见的原因。Bootloader在0x08000000，应用程序在0x08010000。跳转前，必须把中断向量表基地址改到0x08010000。

不同MCU做法不一样：

  • Cortex-M3/M4：写SCB->VTOR寄存器
  • 某些国产MCU：可能没有VTOR，需要在链接脚本里固定向量表位置
  • 老架构：甚至需要自己写汇编跳转
// Cortex-M3/M4 跳转前的标准操作
void jump_to_app(uint32_t app_addr) {
    // 1. 关闭全局中断
    __disable_irq();
    
    // 2. 关闭所有外设时钟（重要！）
    RCC->AHBENR = 0;
    RCC->APB1ENR = 0;
    RCC->APB2ENR = 0;
    
    // 3. 重映射中断向量表
    SCB->VTOR = app_addr;
    
    // 4. 设置主堆栈指针
    __set_MSP(*(volatile uint32_t*)app_addr);
    
    // 5. 跳转到复位向量
    void (*app_reset)(void) = (void (*)(void))(*(volatile uint32_t*)(app_addr + 4));
    app_reset();
}
⚠️ 注意： 跳转前一定要关闭所有外设时钟！我遇到过跳转后UART还在发数据，结果跟应用程序的初始化冲突，直接卡死。

2. 堆栈指针没对齐

ARM Cortex-M要求堆栈指针必须4字节对齐，有些甚至要求8字节对齐。如果应用程序的链接脚本里堆栈地址没对齐，跳转后第一次压栈就崩了。

检查方法：看应用程序的.map文件，确认__initial_sp的地址最后两位是0（4字节对齐）或000（8字节对齐）。

3. 外设状态残留

Bootloader里初始化了定时器、DMA、ADC，跳转前没清理干净。应用程序启动时，这些外设还在跑，中断一来，应用程序的中断向量表还没准备好——砰，跑飞。

我建议的做法：

  • 跳转前把所有用过的外设恢复到复位状态
  • 关闭所有中断（包括NMI，如果可能的话）
  • 清空所有挂起的中断标志

4. 链接脚本地址冲突

Bootloader和应用程序的链接脚本里，有没有重叠的区域？我见过一个案例：Bootloader占用了0x08000000-0x08007FFF，应用程序的ROM起始地址设成了0x08007000——重叠了2000字节。Bootloader跳转后，应用程序的代码把Bootloader的尾巴覆盖了，然后Bootloader的跳转代码本身也崩了。

检查方法：

  • Bootloader的.map文件里，看最后使用的地址
  • 应用程序的链接脚本里，ROM起始地址必须大于Bootloader结束地址
  • 留出至少1KB的“安全缓冲区”

四、调试工具与技巧

最后分享几个我常用的调试手段：

问题类型 调试工具 我的经验
Bootloader不启动 示波器、逻辑分析仪 先看电源和复位，再看时钟，最后看GPIO
校验失败 串口打印、CRC计算器 把收到的每个包都打印出来，跟PC端比对
跳转跑飞 JTAG/SWD调试器 在跳转前设断点，单步进应用程序，看PC指针
💡 终极技巧： 在Bootloader里留一个“调试模式”。按住某个按键上电，Bootloader就不跳转，而是进入一个循环，不断打印关键寄存器的值。这个功能我几乎每个项目都加，调试时省了太多时间。

好了，这一讲的内容就这些。这三个问题，说白了就是“起不来、验不过、跑不稳”。每个问题背后都有固定的排查路径，走熟了就不慌了。
